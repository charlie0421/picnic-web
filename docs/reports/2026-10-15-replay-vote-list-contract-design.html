Replay 투표 목록 계약 설계

작성: 2026-10-15 KST · 기준 HEAD 1f5420c5 · 선행 문서: P0 설계, production 형식 조사, 2026-10-15 핸드오프

목표: 비로그인 /ko/vote ongoing 목록의 PC(1280×900)·모바일(390×900) 화면을 로컬에서 재생할 수 있는 제품용 변환 계약을 정의한다. 개인정보·자유 문자열·검증하지 않은 CSS는 출력에 포함하지 않는다. 이 문서는 핸드오프 §6의 1–3단계(제품 계약, 로컬 구현·반례, 제품 화면 복원)만 다룬다.

이 문서는 제품 연결·운영 활성화의 승인이 아니다. 제품 app/components/lib에서 변환기를 호출하지 않는다. 실제 인증·광고·route 상태 연결, 외부 Sentry 저장, 운영 수집 결정은 별도 단계다.

1. 범위

포함ongoing 목록의 PC·모바일 화면, 배너 클릭 이동(PC 0→2→0, 모바일 0→1→2→3→4), 스크롤 후 지연 이미지 로딩, 이미지 실패 표시. production 조사에서 관측한 상태만 다룬다.
제외upcoming/completed, 더 보기, 필터·언어·메뉴 열기/닫기, API 오류·재시도, popup, 보상·아티스트 변형, 실제 배포 글꼴 URL, 원격 CDN·서명 URL, SSR·hydration 전이, 제품 연결, 운영 활성화, VoteListPresenter.tsx 타이머 수정.
유지controller.ts·transport.ts·correlation.ts·Worker 경계, 예산(입력·해제·출력 각 8 MiB, 깊이 80, 순회 값 200,000, 이벤트 10,000, 노드+tombstone 20,000), type 5 전부 삭제, 실패 시 같은 document에서 영구 CLOSED.

2. 구조

현재 scripts/replay-p0/projection.ts는 tag·class·CSS 규칙을 코드 분기와 fixtures/sdk-contract.json에 직접 둔다. 이 설계는 검증 엔진과 계약 데이터를 분리한다. 모든 코드는 scripts/replay-p0/ 아래에 둔다.

데이터 흐름: SDK envelope → projectEnvelope(input, state, contract) → 새 객체 또는 {ok:false, reason} → 기존 전송 관문. 시작할 때 계약 하나를 고른다. 녹화 중에는 계약을 바꾸지 않는다.

빌드 결합: 제품 계약은 manifest의 빌드 ID·CSS 해시가 수신 값과 일치할 때만 통과한다. 불일치는 schema로 종료한다. 빌드가 바뀌면 manifest를 다시 생성하고 검토한다. 이번 단계는 로컬 .next-envtest 빌드에만 묶는다.

3. DOM·head·shadow·SVG

원칙: 노드는 유지하고 속성을 비운다. 노드를 삭제하면 이후 mutation이 삭제한 ID를 참조할 수 있기 때문이다.

3.1 허용 tag

html, head, body, meta, title, link, style, div, span, a, button, img, svg, header, main, section, footer, h3, p, next-route-announcer. 다른 tag는 schema로 종료한다.

3.2 head

노드출력
meta charset{charset:"utf-8"}. 원본이 상수와 다르면 종료한다.
meta name=viewportmanifest의 viewport 상수만 출력한다. 원본 content가 상수와 다르면 종료한다.
그 밖의 meta속성 없는 <meta>. name·content·property는 출력하지 않는다.
title노드를 유지한다. text 자식은 빈 문자열로 출력한다.
link + _cssText_cssText만 출력한다. 값은 manifest 해시와 일치해야 한다(§4.2). rel·href·crossorigin·data-precedence는 출력하지 않는다.
link placeholder키가 정확히 rr_width·rr_height이고 값이 0px일 때 그대로 출력한다. 다른 키·값이면 종료한다.
styletype="text/css" 상수와 manifest에서 검증한 text만 출력한다. data-styled-jsx는 출력하지 않는다.

3.3 body 속성과 text

  • 출력하는 속성: class(§4.1), style(§4.3), html의 lang="ko", button의 type="button", boolean hidden·disabled(빈 값으로 정규화), aria-hidden·aria-expanded·aria-pressed(true/false), role(button·navigation·list·listitem·alert). 열거값 밖의 값은 종료한다.
  • 출력하지 않는 속성: href, id, name, content, aria-label, aria-live, aria-haspopup, hreflang, crossorigin와 위 목록에 없는 모든 속성.
  • text: 공백이 아닌 문자를 모두 *로 바꾼다. 원본이 이미 마스킹됐다고 가정하지 않는다. comment는 빈 값으로 출력한다.

3.4 media placeholder (img·svg)

  • 허용 키는 정확히 class·rr_width·rr_height다. svg 노드는 isSVG:true도 허용한다.
  • 자식 노드, src·srcset·rr_src, 그 밖의 키가 있으면 종료한다. 차단 실패를 뜻하기 때문이다.
  • 치수 문법: ^(0|[1-9]\d{0,4})(\.\d{1,6})?px$, 값 0…16384. 출력은 소수 셋째 자리로 반올림하고 끝의 0을 지운다. 예: 199.359375px → 199.359px. 최대 오차 0.0005px.

3.5 shadow (Next route announcer)

  • isShadowHost:true는 next-route-announcer 노드에만 허용한다. isShadow:true는 그 직속 자식 div 하나에만 허용한다.
  • 그 div의 style은 manifest의 announcer 상수 문자열과 정확히 같아야 한다. role은 alert다. text는 §3.3 규칙으로 마스킹한다.
  • 다른 위치의 shadow 표식이나 두 번째 shadow는 종료한다. route가 /ko/vote로 고정되므로 보존해도 시각 영향이 없고 삭제 후 참조 처리가 필요 없다.

3.6 mutation과 추가 필드

add 노드는 snapshot과 같은 규칙을 적용한다. attribute·text 변경도 같은 규칙으로 다시 검증한다. remove는 기존 tombstone 규칙을 유지한다. 노드에 위에 없는 필드(예: rootId)가 있으면 종료한다.

4. class·CSS·inline style

4.1 class token

  • 생성기는 검증된 빌드 CSS와 styled-jsx text의 class 선택자에서 token을 추출한다. selector parser로 escape를 해제한 정확한 문자열을 쓴다. Tailwind token, jsx-<hash>, next/font의 __className_*가 포함된다.
  • manifest에 없는 token은 출력에서 제거한다. 예: CSS 규칙이 없는 lucide.
  • production 조사의 class 282종은 생성 결과와 대조하는 시험 입력이다. 허용 근거가 아니다.
  • 예산: 노드당 64 token, token당 256자(P0와 같음). 줄바꿈과 연속 공백은 구분자로 처리한다.

4.2 정적 CSS

  • manifest는 rrweb이 내보내는 표현의 sha256을 저장한다. link는 CSSOM에 SDK 변환을 적용한 _cssText, style은 text 원문이다. 해시가 정확히 같을 때만 통과한다. 출력은 입력 문자열 그대로다.
  • 생성기 절차:
    1. 빌드 원본을 Chromium의 CSSStyleSheet로 파싱해 CSSOM 문자열을 만든다.
    2. 설치된 SDK의 CSS 호환성 변환을 적용한다.
    3. 결과를 저장된 production 캡처의 wire 값과 비교한다.
    4. 하나라도 다르면 manifest를 만들지 않고 실패한다.
  • url(, @import, @font-face의 src: url이 있으면 생성을 거부한다. 따라서 manifest는 font mock(local(Arial)) 빌드에서만 생성된다. 재생은 고정 fallback font를 쓰며 그 차이를 결과에 기록한다.

snapshot 문자열과 mutation diff에 같은 규칙을 적용한다. 범위 밖 값은 clamp하지 않고 종료한다.

4.4 P0 설계에서 바뀐 값

  • 배너 상한: bannerCount(0…100)는 시험 harness가 합성 fixture 값으로 계약에 넣는다. DOM에서 읽지 않는다. 상한은 P0 설계의 totalSlides − slidesPerView 대신 bannerCount − 1을 쓴다. slidesPerView가 viewport·CSS breakpoint에 따라 달라지기 때문이다. 관측 최대값(PC 2, 모바일 4)은 이 범위 안이다. 엄격한 관계식은 실제 데이터 연결 단계에서 다시 검토한다.
  • aspect-ratio: P0 설계 후보(1/1, 16/9, 4/3) 대신 배너 소스 상수 700 / 356을 쓴다.
  • 소수 px: P0의 정수 px 검사 대신 §3.4 문법을 쓴다.

6. 시험과 완료 기준

각 단계를 통과해야 다음 단계를 진행한다.

  1. 엔진 분리 회귀: p0-fixture 계약으로 기존 P0 단위 시험 139개와 브라우저 22개 케이스가 결과 변화 없이 통과한다. 제품 계약 코드는 이 단계 뒤에 작성한다.
  2. 계약 단위 시험(TDD): 규칙마다 통과 예와 거부·제거 예를 1개 이상 둔다. 합성 표식(PIIMARK-…)을 text, aria-label, href, meta content, title, id, style, class, type 5에 넣는다. 압축·비압축 출력 모두에서 표식이 0회여야 한다.
  3. 실제 캡처 투입: wire-1280-*·wire-390-*의 segment 0→1→2가 모두 ok다. 출력 bytes에서 127.0.0.1, /_next/image, http, aria-label 원문이 0회다.
  4. 변조 반례: 실제 캡처에 한 가지씩 변조를 넣고 기대 reason을 확인한다: img src 추가, svg 자식 추가, 배너 인덱스 초과, CSS 1byte 변경, 두 번째 shadow, 미허용 style 속성, source 8 삽입, segment 누락.
  5. 복원 비교: 투영 결과를 replay-view.ts의 독립 DOM 복원으로 재생한다(Chromium, 고정 fallback font). 같은 시각의 원본과 비교한다: 주요 요소(투표 카드, 배너 track, placeholder, 상태 필터)의 위치·크기 1 CSS px 이내, opacity 0.01 이내, 카드·배너 개수와 배너 인덱스 일치. 원본 레이아웃 측정이 부족하면 capture.cjs에 측정 코드만 추가해 다시 수집한다. 제품 코드는 바꾸지 않는다. 마스킹·media·글꼴 차이는 예외로 기록한다. 현재 replay-view.ts는 P0 tag 7개만 복원하고 _cssText·SVG namespace·shadow를 처리하지 않는다. 이 단계에서 §3.1 tag, link _cssText의 style 적용, isSVG 노드의 SVG namespace 생성, announcer shadow root를 지원하도록 확장한다. 확장한 복원기도 투영 상태나 SDK 내부를 쓰지 않는다.
  6. 전체 회귀: npm test, npx tsc --noEmit --incremental false, 범위 ESLint, git diff --check.

완료 기준: 위 6단계 통과와 교차 공급자 코드 리뷰 APPROVE. 개인정보 관련 변경이므로 고위험으로 분류하고 Frontier 리뷰를 받는다. 결과는 docs/reports/의 결과 보고서 HTML로 남긴다. 실패한 단계가 있으면 계약을 넓히지 않고 보고한다.

7. 남는 위험

  • 마스킹한 text의 길이·위치, class 조합, placeholder 치수는 화면 구조 정보를 남긴다. 허용한 시각 구조의 한계로 기록한다.
  • bannerCount − 1 상한은 P0 설계보다 느슨하다.
  • manifest는 font mock 빌드에 묶인다. 실제 배포 빌드에서 그대로 쓸 수 없다.
  • SDK 내부 메모리·재시도의 한계는 P0 설계 §3과 같다. 이 설계는 그 한계를 바꾸지 않는다.
