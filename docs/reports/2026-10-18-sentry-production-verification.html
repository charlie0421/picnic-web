Sentry #73·#74 — 운영 수신 확인

2026-10-19 후속 안내: 아래는 위치 정보 설정 변경 전 조사 기록이다. 이후 GitHub #73·#74는 종료됐고 city·subdivision·region·country_code·ip_address를 추가 제거 필드로 저장했다. 설정 저장 결과와 후속 확인 상태를 참조한다. 아래의 OPEN·빈 필드 목록은 당시 상태다.

2026-10-18 KST · 운영 코드 기준 main 9645c0e6 · 읽기 전용 조사

운영 Sentry에 저장된 서버 오류 2건을 확인했다. 최신 오류와 시각·경로·사건 코드가 일치하는 Vercel 401 응답 기록도 확인했다. 이전의 “확인할 서버 이벤트가 없음” 상태는 해소됐다.

사용자 로그인 뒤 상세 API와 JSON 보기로 두 이벤트를 검사했다. 두 건 모두 Cookie·인증 헤더·요청 쿼리·요청 본문·IP 원문이 없었다. #73·#74에 남아 있던 운영 표본 확인 조건을 충족했다. GitHub 이슈 상태는 OPEN을 유지했다.

별도 관찰: 두 이벤트의 user.geo에 국가·도시·지역 정보가 남아 있다. 조직 전체의 IP 저장 방지는 켜져 있지만 위치 필드는 비어 있지 않다. 위치 정보까지 제거할지는 별도로 결정해야 한다. 원본 요청에 어떤 민감정보가 있었는지는 알 수 없으므로, 이 표본만으로 모든 입력의 제거 성능을 입증하지 않는다.

작업의 뜻과 판정

작업쉽게 설명하면이번 결과
#73 민감정보 제거오류 보고에 쿠키·인증 헤더·요청 쿼리·IP가 저장되지 않았는지 확인한다.두 표본 모두 해당 값 없음. 운영 표본 확인 완료. 위치 정보는 별도 정책 항목이다.
#74 오류 전달서버가 보낸 오류 보고가 실제 Sentry에 도착했는지 확인한다.운영 서버 이벤트 2건의 저장과 수신 시각 확인. 운영 표본 확인 완료. 특정 요청의 after() 완료 시각·flush 성공은 직접 관측하지 못했다. 모든 요청의 전달 성공을 뜻하지 않는다.

저장된 상세 필드 검사

검사 대상두 표본의 결과
request의 Cookie·Authorization·웹훅 서명 및 기타 인증 헤더JSON에 request 자체가 없다. 상세 API에도 request entry가 없다. 헤더·쿠키 원문이 저장되지 않았다.
요청 URL query·query_string·본문없음. 최신 이벤트의 HTTP breadcrumb 2개도 URL query·fragment·내장 자격 증명이 없다. 이전 이벤트에는 breadcrumb가 없다.
user.ip_address·프록시 IP 헤더·request 환경의 IP없음. 상세 API의 user.ip_address는 null이며 JSON의 user에는 geo만 있다.
contexts·extra·breadcrumbs·tags·추적 정보extra 없음. 로그 context에는 timestamp만 있다. 13개 tag는 환경·release·runtime·서비스·고정 transaction 등이다. 전체 JSON에서 Cookie·인증 헤더·민감 키와 JWT·Bearer 토큰 모양을 찾지 못했다. _dsc에도 요청 쿼리나 Replay ID가 없었다.
스택의 ?b59e두 이벤트에서 복원된 app:///…/picnic-web/?b59e 프레임이 각각 2개다. 값 없는 파일 경로 접미사이며 raw_stacktrace에는 query가 없다. 요청 쿼리의 잔존으로 판정하지 않았다. 저장 JSON에 모든 ?가 없다고 주장하지 않는다.
fingerprint와 사건 코드별 이슈 분리두 JSON 모두 ["{{ default }}", "payment.portone.webhook.signature.failed"]다. 같은 코드가 같은 이슈에 묶인 것은 확인했다. 다른 코드의 이슈 분리는 이번 표본으로 검증할 수 없다.
user.geocountry_code·city·subdivision·region 필드가 존재한다. 위치 원문은 기록하지 않았다. 방문자와 서버 중 어느 위치인지는 확정하지 않았다.

상세 API와 화면의 JSON 링크를 기존 브라우저 세션으로 읽었다. 원문은 검사 중 브라우저 메모리에서만 처리했다. 보고서와 Git에는 값의 존재 여부, 안전한 사건 코드, 확인에 필요한 이벤트 ID만 남겼다. 상세 API의 fingerprints 해시와 JSON의 사용자 지정 fingerprint는 구분했다. 조회 방법은 Sentry 개별 이벤트 조회 문서를 따른다.

Sentry 조직 설정 문서에서 조직의 scrubIPAddresses=true는 모든 프로젝트의 새 이벤트에 IP 저장 방지를 적용한다. 따라서 프로젝트 값 false만 보고 IP 저장 방지가 꺼졌다고 판단하면 안 된다. 이번 조회로 기존 설계의 결정 5에 남아 있던 IP 저장 설정을 확인했다. 이벤트 발생 당시 설정 이력은 조회하지 않았다.

Sentry는 이벤트와 연관된 IP에서 위치 정보를 만들 수 있다. 공식 위치 정보 제거 안내는 Additional Sensitive Fields에 city, subdivision, region, country_code, ip_address를 추가하는 방법을 제시한다. 위치 제거를 선택하면 해당 필드 추가와 새 표본 검증이 후속 작업이다. 이번에는 운영 설정을 변경하지 않았다.

검증 범위와 남은 결정

  • #73·#74의 최신 이슈 기록에 남은 조건인 “저장된 운영 서버 이벤트에서 요청 민감정보 부재와 도착 확인”을 충족했다. 이슈 종료나 상태 변경은 수행하지 않았다.
  • 표본 2건에서 저장되지 않은 것은 확인했지만 원본 입력과 비교한 제거 시험은 아니다. 기존 합성 canary·envelope 시험과 이번 운영 관측은 서로 다른 증거다.
  • 운영 위치 정보의 유지 여부, 서로 다른 사건 코드의 이슈 분리, 모든 요청의 전달률은 이번 확인으로 확정하지 않는다.
