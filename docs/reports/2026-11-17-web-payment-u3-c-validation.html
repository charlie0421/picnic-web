웹결제 U3 C 영속 보류 로컬 검증

승인 범위의 D1–D6, W1–W3와 H1을 로컬에서 구현하고 검증했다. 확정 분류 전 장애는 접수를 보류한다. 보호 조회는 OPEN을 확인한 뒤 한 번 실행한다. 실제 adverse 판단은 같은 주문의 후속 CLEAN으로 해제되지 않는다. 운영 관문 OG1–OG6은 닫혀 있다.

실행 결과독립 검토고정 기준증거 매핑남은 제한

근거는 승인 계획과 상세 설계의 검증 계약이다. 개별 원문과 영수증은 승인된 로컬 증거 저장소에서 유지한다.

독립 검토

  • 단위별 RED·GREEN과 독립 검토 결과를 보존했다. 초기 설계와 구현 후보에서 발견한 FAIL/PARTIAL도 원 기록에 남겼다.
  • H1의 Q-M1과 S-L1을 수정했다. 원 리뷰어는 정상 종료 실패 정산과 같은 주문의 실제 재시작 검증을 재확인했다.
  • W 전체 검토는 W-F1 HIGH를 발견했다. 두 관측을 놓치던 non-2xx 경로를 보완했다. 원 리뷰어는 W-F1 FIXED와 한정 SPEC·QUALITY·builder PASS를 기록했다.
  • D 전체 독립 검토 판정은 SPEC PASS / QUALITY PASS(LOW 2) / builder PASS(정적 검토 범위)이다. 리뷰어는 최종 native 영수증과 같은 매니페스트의 기존 D6 기록을 읽었다. 조정자는 그 뒤 D6 반복 실행과 정리를 확인했다.
  • LOW-1. NO_CHANGE와 실패 계열 결과는 각자 카운터를 누적한다. 결과가 교대해도 반대 카운터를 초기화하지 않는다. 현재 시험은 두 포화값 31의 보존을 단언한다. 교대 결과에서도 backoff가 최대 6시간까지 늘어날 수 있다. SQL과 기대값은 유지했다.
  • LOW-2. 후보와 HEALTH의 반복 hold 계산 및 일부 JSON 증거 조회는 운영 규모에서 비용이 커질 수 있다. OG2 전에 실제 데이터 분포와 실행 계획, 대기열 지연을 측정해야 한다.
  • D native 시험은 고정된 계약과 의존성 closure를 설치했다. 운영 DB에 전체 이력 migration chain을 적용한 증거는 없다. SCOPE_ONLY의 구 lease 경계는 cutover의 drain/fence 증거에 의존한다.

실행 수치는 조정자가 실행하고 검증한 것이다. 리뷰어는 고정 소스와 diff, 실제 실행 기록을 읽기 전용으로 대조했다. 단위와 정정 재검증의 읽기 범위를 해당 리뷰이력에 보존했다.

기대값 변경과 실측 한계

  • W2는 intent 이후 직접 receive를 제거했다. 신규 P1 또는 cycle 결과가 확정 전달되지 않으면 같은 호출에서 자동 수정을 반복하지 않는다.
  • GET 404와 표현할 수 없는 실제 adverse는 REVIEW로 남을 수 있다. intent 없는 완료 관측은 W에서 바로 접수하지 않는다. 중복 링크·capture ID 불일치와 기존 sticky hold가 있으면 DB의 확정 결과를 따랐다.
  • W-F1 native probe는 실제 W 분류 모듈이 만든 503 payload를 D RPC에 전달했다. 이후 CLEAN의 승인 판정과 실제 접수 차단을 대조했다. 일반 NO_DATA 대조군만 한 건이 접수됐다. 첫 시험은 reason_code를 outcome으로 잘못 단언해 실패했다. 수정한 시험은 정확한 REVIEW_REQUIRED / INTAKE_HELD 구조를 확인했다.
  • H1 caller8과 extra-O는 각각 assertions와 observed_capture_ids 한 필드를 시험에서 조정한 native 수용성 검증이다. 운영 gateway 최대 크기 측정과 자연 W 출력은 미검증이다.
