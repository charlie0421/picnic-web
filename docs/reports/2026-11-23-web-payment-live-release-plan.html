고객 출시까지의 순서

  1. PostgreSQL 적용 키트를 마무리한다. 선행 5개 해시를 대조하고, current10과 M1–M5를 한 파일씩 적용할 고정 산출물을 검토한다. 각 파일은 SQL 본문과 원장 삽입을 한 트랜잭션으로 실행한다. 격리 PostgreSQL 15.8에서 대상 15개와 첫 파일 원장 충돌의 롤백을 확인했다.
  2. 웹 구매 화면을 서버 주문에 연결한다. U3·U4에 따라 서버가 고정한 견적과 주문을 사용하도록 로컬 코드를 전환했다. 구매 승인 콜백에서만 청구한다. 기존 진입 조건은 샌드박스 검증과 운영 승인까지 유지한다. PayPal Checkout 연결 절차
  3. PayPal 지급 계약을 완성한다. 현재 웹 재조정의 운영 resolver는 닫혀 있다. DB와 지급 검증 워커도 PayPal COMPLETE를 COMPLETION_EVIDENCE_REQUIRED로 보류한다. 승인된 범위에서 서버 전용 자격 증명을 결제 환경, 판매자, 고정 주문 binding에 연결한다. 최초 완료 시점을 입증할 공급자 증거와 DB 수용 조건을 검증한다. 거래 생성 시각이나 최근 갱신 시각을 최초 완료 시각으로 바꾸지 않는다.
  4. 샌드박스에서 결제부터 지급·환불까지 확인한다. 기존 시작점부터 실제 공급자 샌드박스와 서버, 주문·청구·대사·지급 기록을 함께 확인한다. 구매 승인 없는 청구 0건, 중복 청구와 지급 0건, 결과 유실 뒤 보류, 정상 고객의 지급 1건과 환불 시 회수를 검사한다. 고객 출시 전에 운영 점검 도구의 M4 heartbeat 지문, 처리 지연과 경보를 검증한다.
  5. 승인된 작업 창에서 호환 웹 앱과 Supabase 작업자를 배포한다. 적용된 원장과 RPC, 권한, RLS를 확인한다. 웹 등록·청구가 닫힌 상태에서 웹 요청과 리스 종료를 확인한다. 배포 전후 버전, 공용 지갑 작업자의 모바일 구매·환불 처리와 heartbeat 경보를 대조한다.
  6. 승인된 범위에서 고객에게 연다. 운영 자격 증명, 재조정 cron, 실제 공급자 호출 및 COMPLETE를 검증 결과에 맞춰 승인받는다. 제한된 범위에서 운영 확인을 시작한다. 각 승인 및 관측 범위를 기록한다. 미확인 주문의 보류 해제와 실제 ADVERSE 해결은 해당 주문의 운영 절차에 따른다.

서버 주문·구매 화면 로컬 연결

  • PayPal 주문 연결, 청구, 대사, 상태 조회용 새 API를 서버 주문 경로에 추가했다. 서버 세션에서 사용자 ID를 얻고, 청구 요청에는 승인된 PayPal 주문 ID만 허용한다. API에 유효한 주문 ID가 있으면 내부 장애는 고정된 503 DTO로 응답한다.
  • 구매 화면은 명시적 국가 입력과 약관 동의 뒤 서버 견적을 보여준다. PayPal 승인 콜백에서만 청구한다. PayPal 주문 연결을 시작한 뒤 취소, 오류 또는 창 닫힘이 발생하면 대사를 요청한다. 서버 상태가 GRANTED일 때 지급 완료를 표시한다.
  • 같은 탭의 세션 저장소에 주문 요청 ID와 청구 시도 여부를 각각 전송 전에 저장한다. 다른 상품을 선택했거나 이전 견적이 만료되면 이전 주문의 청구 창을 닫아 둔다. 두 경우 모두 서버가 미제출·접수 없음·검토 불필요를 확인하고 이 탭의 청구 시도 기록도 없을 때만 이전 시도를 정리한다. 주문 API가 확정 거절한 경우에도 입력을 바꿀 수 있다. 전송 결과가 불확실하면 같은 요청 ID를 보존한다. 복구 범위는 같은 로그인 세션의 같은 탭이다.
  • 기존 PayPal 주문 생성과 청구 API는 410을 반환한다. 폐쇄 시험에서 인증, DB, 공급자 호출 모두 0회였다. 예전 경로의 두 예상 실패는 폐쇄 회귀로 대체했다. 서버 청구 코어의 소유권·금액 회귀는 유지했다.
  • 샌드박스 UI 검증에는 명시적 PayPal SDK 환경, 공개 client ID, 실제 약관 버전이 필요하다. 서버 자격 증명 조회는 현재 닫혀 있다. 이 구현은 공급자 호출, 실제 앱 세션이나 운영 배포 증거를 포함하지 않는다.
