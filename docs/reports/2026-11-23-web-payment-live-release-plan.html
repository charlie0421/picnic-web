PICNIC 웹 결제 고객 출시 준비

2026-11-23 · 운영 적용 전. PostgreSQL 15.8을 기준으로 한다. 새 PayPal 결제에서 구매 승인부터 지급까지 검증한 뒤 고객에게 연다. 적용 순서는 기존 운영 승인 범위를 따른다.

확인한 운영 상태

2026-11-23 19:18:04 KST에 PICNIC-PROD의 서버 버전과 원장·등록 정보를 읽기 전용으로 조회했다. 서버 버전은 150008, 원장 최신 버전은 20261120120000이다. 선행 5개의 원장 이름과 단일 SQL 텍스트의 SHA256이 고정 소스와 일치했다. 대상 15개는 모두 미적용 상태다. 웹 공급자 설정 테이블은 없으며, 공용 지갑 작업자 cron은 활성 1개, 웹 재조정 cron은 0개다. 적용 작업 창에서 다시 조회한다.

고객 출시까지의 순서

  1. PostgreSQL 적용 키트를 마무리한다. 선행 5개 해시를 대조하고, current10과 M1–M5를 한 파일씩 적용할 고정 산출물을 검토한다. 각 파일은 SQL 본문과 원장 삽입을 한 트랜잭션으로 실행한다. 격리 PostgreSQL 15.8에서 대상 15개와 첫 파일 원장 충돌의 롤백을 확인했다.
  2. 웹 구매 화면을 서버 주문에 연결한다. 화면은 현재 기존 PayPal API를 호출하고 팝업이 닫히면 청구를 시도한다. 기존 계획의 U3·U4에 따라 서버가 고정한 견적과 주문으로 전환한다. 구매 승인 콜백에서만 청구하고, 팝업 닫힘은 상태 조회로 처리한다. 타인 주문과 가격 불일치를 청구 전에 거부하는 두 기존 예상 실패를 정상 통과로 전환한다. 고객 전환 전까지 새 진입 스위치를 닫아 둔다. PayPal Checkout 연결 절차
  3. PayPal 지급 계약을 완성한다. 현재 웹 재조정의 운영 resolver는 닫혀 있다. DB와 지급 검증 워커도 PayPal COMPLETE를 COMPLETION_EVIDENCE_REQUIRED로 보류한다. 승인된 범위에서 서버 전용 자격 증명을 결제 환경, 판매자, 고정 주문 binding에 연결한다. 최초 완료 시점을 입증할 공급자 증거와 DB 수용 조건을 검증한다. 거래 생성 시각이나 최근 갱신 시각을 최초 완료 시각으로 바꾸지 않는다.
  4. 샌드박스에서 결제부터 지급·환불까지 확인한다. 기존 시작점부터 실제 공급자 샌드박스와 서버, 주문·청구·대사·지급 기록을 함께 확인한다. 구매 승인 없는 청구 0건, 중복 청구와 지급 0건, 결과 유실 뒤 보류, 정상 고객의 지급 1건과 환불 시 회수를 검사한다. 고객 출시 전에 운영 점검 도구의 M4 heartbeat 지문, 처리 지연과 경보를 검증한다.
  5. 승인된 작업 창에서 운영 DB와 앱을 전환한다. 웹 등록·청구를 닫은 상태에서 웹 요청과 리스 종료를 확인한다. 공용 지갑 작업자의 모바일 구매·환불을 보존한다. 고정된 15개 파일을 적용한 후 원장, RPC, 권한, RLS와 경보를 확인한다. 호환 웹 앱과 Supabase 작업자를 배포하고, 적용 전 상태와 비교한다.
  6. 승인된 범위에서 고객에게 연다. 운영 자격 증명, 재조정 cron, 실제 공급자 호출 및 COMPLETE를 검증 결과에 맞춰 승인받는다. 제한된 범위에서 운영 확인을 시작한다. 각 승인 및 관측 범위를 기록한다. 미확인 주문의 보류 해제와 실제 ADVERSE 해결은 해당 주문의 운영 절차에 따른다.
