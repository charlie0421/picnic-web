Replay 제한 수집 설계

2026-10-14 · 소스 기준 ec2275f6 · 정책 초안 074c3606 · SDK 9.47.1 · 구현 전 설계

첫 구현의 목표는 “언제든 확실히 멈출 수 있는지”를 입증하는 것이다. 합성 데이터만 쓰는 격리된 브라우저 시험에서 차단 경계를 먼저 검증한다. 실패하면 그 페이지의 Replay를 영구 종료한다. 자동 재개·오류 시 버퍼링은 도입하지 않는다. 운영 수집률은 계속 0/0이며, 이 문서는 활성화 승인이 아니다.

이 문서는 수집 현황과 허용 기준 초안을 구체화한다. 의도한 결과는 비로그인 투표 목록의 배너·레이아웃·상태 변화를 필요한 범위에서 재생하는 것이다. 개인정보·자유 문자열·미확인 CSS를 전송하지 않는 기준과 재생 품질을 함께 검증한다. 아래 수치와 제한은 새 설계의 제안값이며, 현재 제품의 보장이나 측정 결과가 아니다.

1. 선택한 구조와 범위

방안판단
선택: 전송 직전의 엄격한 변환 + 시작·종료 제어기존 압축 처리와 envelope 검증을 활용하되, Replay 전용 차단 상태와 직렬 처리를 추가한다. 녹화 중 브라우저 메모리에 생기는 원본까지 없앤다고 주장하지 않는다.
SDK 공개 훅만 사용beforeAddRecordingEvent는 custom event만 처리한다. DOM·CSS 전체의 허용 기준을 충족할 수 없다.
녹화기 fork 또는 자체 recorder메모리에 넣기 전 필터를 적용할 수 있는 후보지만 버전 추적·브라우저 호환성·재생 검증 부담이 커진다. 첫 구현에 포함하지 않는다. 선택한 구조가 필수 중단 조건을 증명하지 못하면 별도 설계로 판단한다.
  1. ① 상태 제어
    시작 조건 확인·종료 고정
  2. ② SDK 녹화
    마스킹·영역 차단
  3. ③ Replay 변환
    허용 필드로 새 객체 생성
  4. ④ 전송 관문
    세대·상태 재검사 후 전송

오류·성능 등 일반 Sentry 이벤트는 기존 transport와 필터를 사용하되, Replay가 추가하는 연결 식별자는 별도 제거한다(아래 §3). Replay envelope의 내용 변환·전송 관문은 별도 경로로 처리한다. Replay item과 다른 item이 섞인 envelope는 분리하여 일부를 보내지 않고 전체를 거부한다. 미확인 형식을 통과시키는 fallback은 두지 않는다.

첫 제품 적용 후보: 정확한 /ko/vote, 빈 query·fragment, 인증 초기화 완료 및 비로그인 확인, 광고 미동의 확정 및 해당 document에서 광고 SDK가 한 번도 실행되지 않은 상태. canLoadAds=false 하나만으로 이 조건을 충족했다고 판단하지 않는다. 저장값 없음·파싱 오류·상태 미확인은 시작 불가다. 다른 언어·상세·로그인·구매·사용자 메뉴·서버 HTML·모든 iframe은 대상 밖이다. 광고 동의와 Replay의 수집 근거·동의는 별개이며, 운영 적용 전에 후자를 별도로 확정해야 한다.

세대 번호는 시작·종료 시 증가시키는 로컬 정수다. 비동기 import·압축 처리·전송 작업은 시작 당시 세대를 보유한다. 작업 결과를 쓰기 전과 실제 네트워크 호출 직전에 현재 세대와 다시 비교한다. 페이지가 숨겨지거나 pagehide가 발생하면 종료한다. BFCache 복귀도 같은 document에서는 종료 상태를 유지한다. 다른 탭의 뒤늦은 알림만으로 녹화 전 차단이 보장된다고 가정하지 않는다.

인증·광고·개인 영역의 상태를 바꾸는 코드가 React 상태 반영 또는 외부 스크립트 삽입 전에 동기적으로 관문을 닫아야 한다. route effect·MutationObserver로 변경 후 감지하는 방식은 이 요구를 만족하지 않는다. 앱이 제어하는 navigation·인증 결과 전달·동의 갱신 경로를 모두 검증하고, 서버 응답·라우터 commit·외부 탭 등 순서를 통제할 수 없는 경로가 하나라도 남으면 해당 화면을 활성화하지 않는다. 초기 격리 시험은 이 경로를 합성 상태로 주입하며, 실제 인증 흐름을 바꾸지 않는다.

3. 종료 순서와 SDK의 한계

  1. 동기적으로 전송 관문을 닫는다. 상태를 CLOSED로 고정하고 세대를 증가시킨다. 이 동작은 SDK의 Promise를 기다리지 않는다.
  2. 소유한 작업을 취소한다. 대기 envelope·변환 상태·노드 맵의 참조를 해제하고, 변환 Worker 및 소유한 fetch의 AbortController를 종료한다. 늦게 끝난 작업은 세대 불일치로 폐기한다.
  3. 공개 Replay.stop()을 호출한다. 호출 중 발생하는 flush도 닫힌 관문에서 거부한다. stop()만 호출하고 전송 허용 상태를 남기지 않는다.
  4. 종료를 관측한다. 앱 소유 참조·타이머·fetch가 정리되고 SDK recorder가 멈췄는지 격리 시험에서 확인한다. 실패 시 시작 불가 상태를 유지한다.

SDK 9.47.1의 공개 stop()은 session 모드에서 forceFlush=true로 내부 stop을 호출한다. 내부 stop은 리스너·recorder를 제거한 뒤 강제 flush를 기다리고, event buffer를 파괴한다. 그러나 이미 finish()로 꺼낸 데이터는 sendReplay의 비동기 처리나 재시도 closure에 남을 수 있다. 정지한 상태에서 flush()를 호출하면 SDK가 새 session을 시작할 수도 있다. 공개 getReplay()와 client.getIntegrationByName('Replay')로 다른 모듈도 인스턴스를 얻을 수 있다. 공개 API에는 영구 비활성화 기능이 없으므로, 모듈 안에 변수를 두는 것만으로 재시작을 막았다고 주장하지 않는다. 앱의 정상 호출은 제어 모듈 하나로 제한하고, 그 밖의 getReplay/getIntegrationByName('Replay')/replayIntegration/start/flush 사용을 정적 검사한다. 외부 코드가 직접 공개 API를 호출하는 반례에서는 메모리 녹화가 다시 시작될 수 있지만 닫힌 전송 관문은 유지돼야 한다. 이 설계는 임의 스크립트의 SDK 직접 호출까지 막는 recorder 보안 경계가 아니다.

보장할 경계: 관문 종료 이후 새 Replay 네트워크 요청을 시작하지 않는다. 이미 전송된 bytes는 되돌릴 수 없으며 abort 성공도 서버 미수신의 증거가 아니다. 따라서 전송이 시작된 데이터는 이미 허용 기준을 통과해야 한다. “비허용 상태 전송 0건” 검증은 차단 시점 이후의 새 호출과 비허용 DOM 데이터가 outgoing/stored payload에 포함되지 않는 것을 각각 확인한다.

메모리 한계: 참조 해제와 Worker 종료는 JavaScript heap의 즉시 물리적 삭제를 뜻하지 않는다. SDK 내부 비동기 작업의 참조·재시도까지 공개 API로 즉시 취소할 수 있다고 가정하지 않는다. 이 설계는 첫 격리 시험에서 그 수명과 종료 동작을 확인한다. 정상 앱 호출 경로에서 recorder가 멈추지 않으면 제품 연결을 중단한다. SDK 내부 재시도의 일시적인 원본 보관은 아래 별도 정책 제안으로 다룬다. 강한 메모리 삭제나 임의 공개 API 호출 후에도 녹화 0회를 요구하면 이 구조를 채택하지 않는다.

재생 손실: 관문을 닫으면 강제 flush도 거부하므로 마지막 미전송 구간은 사라진다. 정상 시간 종료·페이지 숨김에도 적용한다. 이미 전송된 정상 구간만 재생할 수 있으며, 마지막 사용자 동작까지 보존하는 설계가 아니다.

전송 실패와 재시도를 명시적으로 다룬다

현재 withReplayScrubbing은 최대 30개의 비동기 작업을 병행하고, 기존 makeFetchTransport에 넘긴 요청을 취소할 수 있는 핸들을 제공하지 않는다. 이를 그대로 사용해 종료를 보장하지 않는다. 제안하는 Replay 경로는 한 번에 한 envelope만 처리한다. 처리 중 추가 segment가 들어오면 쌓지 않고 전체 Replay를 종료한다.

첫 시험에서는 Replay 전용 fetch 어댑터가 검증된 bytes만 받고 keepalive=false·credentials=omit·referrerPolicy=no-referrer·redirect=error·AbortController를 사용한다. endpoint는 검증 환경의 고정 endpoint(P0에서는 로컬 수신기)이며, 이벤트에서 읽지 않는다. 일반 transport의 queue·retry에 Replay를 넣지 않는다. HTTP 실패·timeout·abort·필터 실패·관문 종료는 잡아서 {statusCode: 403} 형태의 로컬 종료 응답으로 resolve하고, 관문도 닫는다. 이 값은 실제 HTTP 응답으로 기록하지 않는다. 실제 HTTP 2xx일 때만 성공 응답을 전달한다. 429·rate-limit 헤더도 종료로 처리하며 재시도하지 않는다.

이 응답 방식은 9.47.1의 sendReplayRequest가 non-2xx를 TransportStatusCodeError로 처리하고 sendReplay가 그 오류를 재시도하지 않는 코드에 근거한 검증 대상이다. transport 밖의 prepareReplayEvent에서 processor가 예외를 내면, SDK는 원본 recordingData를 closure에 둔 채 5·10·30초 간격으로 최대 3회 재시도한다. 이는 소스에서 확인된 동작이며, 시험에서 새로 발견할 불확실성으로 다루지 않는다. processor가 매번 즉시 실패하는 경우 대기 합계는 45초이고 실제 보관 시간에는 처리 시간도 더해진다. 해결되지 않는 Promise에는 이 45초 상한을 적용할 수 없다. 압축 Worker 응답 대기 또한 별도 무한 대기 반례로 시험한다.

정책 선택 제안: 첫 격리 시험에서는 이 SDK 내부 재시도를 허용하되, 관문 폐쇄 이후 네트워크 요청 0회와 재시도 종료 후 참조 정리를 요구한다. 정상·유한 예외 fixture의 정리 목표는 60초다. 무한 processor/Worker 대기는 예상 실패로 분류하고, 이 반례에서 60초가 지났다고 원본 폐기 성공으로 기록하지 않는다. 60초는 시험의 판정 기한이며 공개 SDK가 강제하는 메모리 수명 상한이 아니다. SDK 재시도는 전송 어댑터의 재시도 금지와 구별한다. 일반 경로에서는 앱 소유 processor의 예외를 포착하고 비동기 대기를 제한하되, 이것만으로 SDK 내부 전체의 수명을 보장했다고 간주하지 않는다.

이 제안은 이전 초안의 “대기 원본·큐 폐기”를 즉시 완료해야 하는 조건보다 완화된 선택이다. 운영에 적용하려면 일시 보관의 수용 여부를 별도로 확인해야 한다. 즉시·강제 폐기가 필수이면 현재 SDK의 공개 API만 쓰는 구조는 부적합하다는 결론을 유지한다. 시험은 알려진 45초 재시도와 무한 대기 반례를 회귀 증거로 남기며, 전체가 제품 적용에 적합하다는 결론을 자동으로 내리지 않는다. 실패 응답·SDK stop·flush 사이의 재진입을 검사하고 transport의 응답 반환 안에서 stop의 완료를 기다려 서로의 flush lock을 기다리는 구조를 만들지 않는다.

다른 이벤트에 붙는 Replay 연결 정보도 제거한다

SDK는 일반 error/transaction의 tags.replayId, feedback의 contexts.feedback.replay_id, 동적 샘플링 문맥(DSC)의 replay_id를 추가한다. DSC는 envelope trace header와 outgoing baggage로 전파될 수 있다. 재시도는 전역 scope의 contexts.Replays에도 진단 상태를 남긴다. replay_event의 error_ids/trace_ids만 비우는 것으로 이 연결이 없어지지 않는다.

초기 정책은 이 연결을 보존하지 않는 것이다. 일반 envelope도 최종 전송 직전 위 tags/context 및 header.trace.replay_id를 제거한다. 격리 시험 client는 tracePropagationTargets=[]로 SDK가 API 요청에 tracing/baggage를 붙이지 않게 하고, 수동 trace header 생성과 feedback integration은 사용하지 않는다. 생성된 일반 이벤트·envelope header·실제 outgoing 요청 header를 녹화 중과 폐쇄 후 모두 검사한다. 제품에서 같은 제거 순서와 요청 헤더 차단을 공개 API로 보장할 수 있는지는 별도 연결 조건이며, 일반 이벤트를 그대로 통과시키면서 연결이 제거됐다고 주장하지 않는다. HTTP 접속 자체의 IP 관측·서버 보관은 payload에서 IP 필드를 제거하는 것과 별개다.

4. envelope·구간·노드 계약

기존 객체에서 위험한 일부 키를 지우는 방식 대신, 검증한 값으로 새 출력 객체를 만든다. raw envelope·오류 문자열·거부값을 console·Sentry·스토리지에 남기지 않는다. 진단은 고정 reason code와 개수만 사용한다. 모든 metadata·header도 이 규칙을 적용한다.

대상제안 계약
envelope정확히 하나의 replay_event와 하나의 replay_recording 쌍. 이벤트·recording payload의 header·직전 상태의 segment 번호를 비교한다. 첫 구간은 0, 이후는 직전+1이어야 한다. envelope event_id·replay_event의 event_id/replay_id·현재 session의 ID가 일치해야 한다. recording payload header에는 segment_id만 요구한다. envelope header도 검증된 SDK 이름·버전·고정 DSN 등 필요한 값으로 재생성한다. 임의 header·trace·attachment는 허용하지 않는다.
순서세션당 replay ID 하나. 첫 segment는 0이고 meta와 full snapshot이 필요하다. 이후 segment는 직전 성공 번호+1만 허용한다. 성공은 HTTP 2xx와 rate-limit 없음으로 판정한다. 번호 누락·중복·replay ID 변경·full snapshot 상태 불일치는 종료한다. segment>0의 추가 full snapshot도 종료한다. recorder 재시작은 mirror.reset()으로 ID 맵을 새로 만들 수 있으므로 기존 맵에 합치지 않는다. 모든 추가 snapshot이 반드시 ID를 재배정한다고 가정하는 규칙은 아니다. 손상 구간을 건너뛰어 복구하지 않는다.
상태 적용변환은 이전의 검증된 상태 복사본에서 수행한다. 전체 envelope 검증과 전송 성공 후에만 다음 상태를 채택한다. 실패하면 맵 전체를 폐기한다. 서로 다른 Replay나 페이지 사이에 맵을 공유하지 않는다.
노드 관계rrweb 숫자 ID를 유지하고 tag·허용 상태·부모·자식 관계를 추적한다. add/move/remove의 부모·nextId·대상 존재를 이벤트 순서대로 확인한다. 같은 ID의 합법적인 이동·삭제 후 재삽입은 SDK fixture로 확인한 순서만 지원한다. 누락 참조·순환·재정의 모호성은 종료한다. segment마다 맵을 초기화하지 않는다.
차단 영역SDK 공개 block 옵션(내부 rrweb의 blockSelector)으로 iframe·개인 영역·미디어를 녹화 단계부터 차단한다. 전송 단계는 허용된 크기·검증된 class만 있는 placeholder를 요구한다. 차단해야 할 subtree가 원문 형태로 들어오면 전체 종료한다. 삭제한 subtree의 ID가 이후 이벤트에 나오면 무조건 통과시키지 않는다. 초기 범위의 placeholder에는 자식·실제 src·rr_src가 없어야 한다.
replay_eventtype="replay_event", replay_type="session", 같은 검증된 32자리 hex replay_id/event_id, segment_id, 초 단위 timestamp/replay_start_timestamp, manifest의 고정 release/environment/platform/SDK 식별값을 생성한다. urls=["https://replay.invalid/ko/vote"], error_ids=[], trace_ids=[]로 고정한다. user·IP·request·contexts·tags·extra는 제외한다. 필수 metadata를 이 계약으로 보낸 결과를 저장 시험에서 확인한다. 추가 필드가 필요하면 계약을 검토하며 원문을 자동 복구하지 않는다.

5. DOM·CSS 값을 남기는 기준

항목첫 범위의 값
text·inputmaskAllText/maskAllInputs/blockAllMedia=true 유지. 보통 text는 출력 단계에서도 공백·별표만 생성한다. 원문을 “이미 마스킹됐겠지” 하고 통과시키지 않는다. 길이·공백·노드 개수·위치로 남는 정보는 허용한 시각 구조의 한계로 기록한다.
class검토한 빌드 manifest의 정확한 token 집합과 필요한 정적 상태 조합만 허용한다. jsx-*, data-*, Tailwind arbitrary value의 접두어 허용은 없다. 알 수 없는 token은 제거하고 시각 비교에서 손실을 평가한다.
HTML id·참조첫 범위에서 id·for·aria-controls·aria-labelledby·name은 제거한다. ID 기반 CSS가 필요하면 초기 범위를 통과시키지 않고 별도 관계 치환 설계를 추가한다. rrweb 숫자 ID와는 무관하다.
상태·기타 속성필요한 hidden·disabled·aria-hidden·aria-expanded는 각 HTML/ARIA 표현을 boolean으로 검증 후 정규화한다. 초기 role은 검토된 button/navigation/list/listitem만 후보. title·alt·aria-label·value·checked·selected·data 속성·head meta content는 원문을 남기지 않는다. 필요한 정적 viewport/charset 값은 manifest 상수로 만든다.
주소·리소스href·src·srcset·action·poster·background·xlink:href·rr_src와 미확인 주소 속성은 제거한다. iframe·SVG·media는 이미 차단돼야 한다. CSS url/import·data/blob·외부 폰트는 초기 범위에서 허용하지 않는다. 재생 환경은 검증된 고정 fallback font를 사용하며 해당 손실을 명시한다.
정적 CSS빌드별 CSS·styled-jsx를 검토해 manifest를 만든다. rrweb이 실제로 내보내는 style text·_cssText의 정규화된 표현도 별도 해시로 고정한다. 캡처한 값을 첫 관측이라는 이유로 자동 승인하지 않는다. 정적 CSS의 URL/폰트/고정 문자열·선택자 참조는 검사하여 제거 또는 계약된 상수로 변환한 출력만 보낸다. 미일치는 종료한다.
동적 inline stylesnapshot/전체 교체의 문자열은 CSS parser로 분리하고 각 속성의 grammar로 새 문자열을 만든다. mutation 객체 diff는 {property: string | [string, priority] | false}만 지원한다. string과 tuple의 값에 같은 grammar를 적용하며 priority는 빈 값 또는 important만 허용한다. false는 검증된 기존 속성의 삭제다. attributes 값 null은 해당 속성 전체 삭제이며 style null이면 저장한 style 상태를 비운다. style diff는 기존 검증 상태에 순서대로 적용해 결과 전체도 재검증한다. 잘못된 구문·중복 속성·미허용 단위·이스케이프·함수·허용 목록 밖 custom property·객체 구조는 종료한다. raw style이나 JSON.stringify 결과를 그대로 복사하지 않는다. CSS.supports 통과만으로 승인하지 않는다.

일반 DOM tag 목록도 빌드에서 필요한 안전한 HTML 요소로 고정한다. script·base·iframe·object·embed·사용자 정의 요소·shadow root의 새 구조는 초기 범위에서 허용하지 않는다. script 등 SDK가 생략하는 노드도 출력 검증에서 재확인한다. 특수 속성도 개별 계약으로 처리한다. rr_width/rr_height는 차단 placeholder에서 0…16384px 정수만, rr_scrollLeft/rr_scrollTop은 검증된 노드에서 −65536…65536 정수만 허용한다. _cssText는 static manifest의 허용 입력 해시와 출력 CSS가 일치할 때만 허용한다. rr_src·rr_dataURL 등 그 밖의 rr_ 속성은 제거한다. 특수 속성이나 style/link 구조의 미확인 형식을 일반 data 속성처럼 허용하지 않는다.

동적 값의 제안 한도

아래 한도는 390×900·1280×900·768×900·1024×900 시험 화면용이다. 범위를 벗어나면 clamp하여 정상으로 보이게 하지 않고 종료한다. 숫자의 양자화는 허용 범위를 먼저 확인한 뒤 수행한다. 음수·NaN·Infinity·지수 표기·불필요한 자유 문자열을 값으로 통과시키지 않는다.

속성/상태정확한 초기 규칙

이 목록은 이전 런타임 관측의 15개 inline CSS 속성을 다루는 좁은 제안이다. 실제 모든 값·애니메이션을 지원한다고 주장하지 않는다. CSSOM source 8·13·15를 중단하는 결정 때문에 라이브러리나 styled-jsx가 녹화 시작 후 규칙을 추가하면 초기 설계가 그 화면을 지원하지 못할 수 있다. manifest 작성과 실제 recorder 시험에서 이 비용을 먼저 판정한다. 숫자·enum에 정보를 인코딩하는 임의 악성 스크립트까지 안전하다는 보장은 하지 않는다.

7. 첫 구현에서 증명할 항목과 후속 경계

첫 구현 범위는 격리된 lifecycle 시험이다. 실제 사용자·광고·Supabase 세션을 사용하지 않는다. P0는 프레임워크의 head·announcer가 없는 독립 정적 HTML로 만든다. 기존 scripts/envelope-test에서는 로컬 수신기·envelope 분석 유틸리티만 재사용하고 App Router fixture page·layout·globals.css는 가져오지 않는다. 같은 lockfile의 npm Replay 코드를 별도 시험용 JS 번들로 로드한다. 초기 HTML에는 P0 tag 목록만 두며 meta·title·stylesheet link·Next.js 생성 노드·shadow root는 넣지 않는다. UTF-8은 로컬 HTTP Content-Type 응답 헤더로 지정한다. viewport는 브라우저 시험 설정으로 고정한다. SDK가 생략하는 script 요소도 출력에 남지 않는지 검증한다. 시험 HTML·번들은 제품 빌드에 포함하지 않는다. CDN loader와 기존 window.Sentry 재사용은 피한다. 최종 JS chunk·SDK 버전·Git SHA를 같이 기록한다. 이 선택은 실제 제품의 lazy loader 교체까지 이번에 승인한 것이 아니다.

첫 시험 전용 최소 계약 P0

P0는 아래 합성 fixture만 허용한다. 제품 전체 manifest와 decoder를 먼저 구현하는 범위가 아니다. 다음 정상 데이터를 실제 SDK가 기록한 3개 이상의 연속 segment로 전송·재생하는 양성 시험이 필수다. 모든 데이터를 거부하는 구현은 실패다. 음성 시험의 canary 0·미허용 필드 0은 이 P0 계약을 기준으로 판정하며 제품 전체 허용 목록 통과로 확대하지 않는다.

P0 항목정확한 범위
