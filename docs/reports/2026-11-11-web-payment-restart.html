3. 현재 PayPal은 어떻게 동작하는가

클라이언트가 SDK를 초기화하고 주문 생성 API를 호출한다. 서버는 인증 사용자와 DB 상품으로 USD 주문을 만든다. 클라이언트는 PayPal 팝업이 닫힌 뒤 capture API를 호출한다. API는 외부 결제를 먼저 확정하고 소유자·금액을 검사한 다음 process_paypal_capture RPC를 호출한다.

항목확인 결과
UI 노출국내·영문 모두 PayPal만 표시. PORTONE_WEB_PAYMENT_ENABLED=false. 구매 버튼은 isAdminProfile 기준으로 제한된다. API 자체는 로그인·탈퇴 여부를 검사하므로 UI 제한을 서버 개방 제어로 간주할 수 없다.
운영 설정현재 Vercel Production 변수 목록에 PAYPAL_*, NEXT_PUBLIC_PAYPAL_* 없음. PortOne 관련 변수 6개는 존재한다. 값·채널 유효성은 미확인.
소유자·금액 검증capture 이후 검사한다. 타인 주문 또는 잘못된 금액을 확정한 다음 적립만 거부할 수 있다. stash의 사전 GET 검증이 출발점이다.
거래 식별자웹은 p_capture_id: captureData.id를 보낸다. Orders capture 응답의 최상위 ID는 주문 ID다. 배포된 워커는 /v2/payments/captures/{providerTransactionId}를 조회하므로 실제 하위 capture ID와 구분해야 한다.
메타데이터웹 주문은 userId/productId, 운영 워커는 user_id/product_id를 읽는다. PortOne도 웹의 customData 구조와 워커의 기대 형식을 함께 맞춰야 한다.
적립 완료 판단운영 RPC는 접수 대기열에 넣는다. PayPal 웹 API는 응답을 즉시 성공으로 취급한다. PortOne verify API는 completed 영수증을 기다리므로 같은 결함으로 단정하지 않는다. 접수·검증·적립·실패 상태와 재접속 복구를 분리해야 한다.
완료 복구팝업 닫힘을 계기로 capture를 시도하고 예외를 숨긴다. 팝업 차단·취소·시간 초과·capture 성공 후 내부 실패를 구분하는 화면과 서버 복구가 필요하다.
중복 요청의 상태 반환PayPal 웹의 중복 조회는 orderID·platform=web을 사용한다. 현재 지갑 계약의 capture ID·공급자·환경 키와 맞지 않는다. 재호출은 소유자와 환경을 확인한 같은 주문의 현재 상태를 반환해야 한다.
결제 도중 상품 변경주문 생성과 capture가 서로 다른 시점의 현재 상품 가격을 읽는다. 로컬 지갑 SQL도 적립 시점의 현재 지급량을 읽는다. 결제 도중 가격 변경이나 대기열 지연 중 보너스 변경에 대비해 견적·지급량의 불변 스냅샷과 유효기간 정책이 필요하다. 로컬 소스와 현재 배포 버전의 일치는 추가 확인 대상이다.
PortOne 환경 구분클라이언트는 NEXT_PUBLIC_PORTONE_ENV, 웹훅은 NODE_ENV로 결제 환경을 정한다. 배포 환경과 결제의 테스트/운영 환경이 다를 수 있으므로 주문·채널·웹훅의 환경 계약을 맞춰야 한다.

6. 권고하는 진행 순서와 구현 경계

9. 두 결제수단 준비 설계

사용자는 가상화폐를 다음 단계로 미루고, PayPal과 PortOne을 함께 준비해 준비된 수단부터 순차 개방하기로 선택했다. 첫 환불 접수 방식은 문의 접수 → 운영자 확인 → 결제사 콘솔 처리이며 결과와 지갑 회수 상태를 웹에 동기화한다.

후속 Astra 계약 조사와 Fable 독립 리뷰를 반영한 웹결제 준비 설계에 서버 주문·견적·상태·복구·환불·국가별 화면과 개방 조건을 정리했다. Fable 1차 지적 High 2·Medium 4·Low 2는 재검토에서 7건 해소·1건 반박 수용으로 정리됐고 기술설계는 통과했다. 재검토의 추가 권고 Medium 2·Low 3은 조정자가 소스와 대조해 문장에 반영했으며 세 번째 모델 리뷰는 하지 않았다. 사용자 설계·회수 정책 승인은 대기 중이다. 이 후속 준비에서 제품 코드·운영 설정을 변경하거나 메일을 발송하지 않았다.
