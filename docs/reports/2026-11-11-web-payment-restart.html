3. 현재 PayPal은 어떻게 동작하는가

클라이언트가 SDK를 초기화하고 주문 생성 API를 호출한다. 서버는 인증 사용자와 DB 상품으로 USD 주문을 만든다. 클라이언트는 PayPal 팝업이 닫힌 뒤 capture API를 호출한다. API는 외부 결제를 먼저 확정하고 소유자·금액을 검사한 다음 process_paypal_capture RPC를 호출한다.

항목확인 결과
UI 노출국내·영문 모두 PayPal만 표시. PORTONE_WEB_PAYMENT_ENABLED=false. 구매 버튼은 isAdminProfile 기준으로 제한된다. API 자체는 로그인·탈퇴 여부를 검사하므로 UI 제한을 서버 개방 제어로 간주할 수 없다.
운영 설정현재 Vercel Production 변수 목록에 PAYPAL_*, NEXT_PUBLIC_PAYPAL_* 없음. PortOne 관련 변수 6개는 존재한다. 값·채널 유효성은 미확인.
소유자·금액 검증capture 이후 검사한다. 타인 주문 또는 잘못된 금액을 확정한 다음 적립만 거부할 수 있다. stash의 사전 GET 검증이 출발점이다.
거래 식별자웹은 p_capture_id: captureData.id를 보낸다. Orders capture 응답의 최상위 ID는 주문 ID다. 배포된 워커는 /v2/payments/captures/{providerTransactionId}를 조회하므로 실제 하위 capture ID와 구분해야 한다.
메타데이터웹 주문은 userId/productId, 운영 워커는 user_id/product_id를 읽는다. PortOne도 웹의 customData 구조와 워커의 기대 형식을 함께 맞춰야 한다.
적립 완료 판단운영 RPC는 접수 대기열에 넣는다. 웹은 응답을 즉시 성공으로 취급한다. 접수·검증·적립·실패 상태와 재접속 복구를 분리해야 한다.
완료 복구팝업 닫힘을 계기로 capture를 시도하고 예외를 숨긴다. 팝업 차단·취소·시간 초과·capture 성공 후 내부 실패를 구분하는 화면과 서버 복구가 필요하다.

4. 가상화폐 적용 가능성

기술적으로 가능하지만 기존 코드를 그대로 이식할 수는 없다. 현재 PICNIC의 구매 공급자 검증 목록에는 NOWPayments가 없다. DB·지갑 워커 확장은 소유 저장소 picnic-supabase에서 별도 변경해야 한다.

vocaloff

NOWPayments hosted invoice, USDT TRC20, sandbox/live 분리, HMAC-SHA512 검증, finished 이후 멱등 RPC 적립 구조가 있다. 일반 사용자 개방 커밋 a0500fc도 확인했다. 이번 조사에서 실거래 성공은 확인하지 않았다.

검토 지점: actually_paid(가상자산 수량)와 price_amount(법정화폐 가격)를 직접 비교한다. 자산·네트워크·정확한 견적 수량을 검증하도록 바꿔야 한다. 서명 검증은 최상위 키만 정렬하므로 공식 규격과 중첩 데이터 대조가 필요하다.

firsttype-web

NOWPayments 인보이스·웹훅 코드가 있지만 crypto checkout은 관리자 전용이다. 일반 충전 개방 계획은 2026-04-21 취소 기록이 있다.

검토 지점: pending 입금행 생성→잔액 RPC→completed 갱신이 별도 호출이다. 중간 실패 뒤 재전송이 기존 행 존재만 보고 성공 처리되면 적립 누락이 고착될 수 있다.

가상화폐는 지원 국가·사업자 수용 여부, 최소 결제액, 네트워크 수수료, 부족 입금·만료·환불, 회계·정산 조건 확인 후 선택한다. 과거 문서의 “전 세계 지원”·고정 수수료 수치는 현재 근거로 사용하지 않는다. NOWPayments 공식 API와 IPN 안내를 대조했다. 검색된 구약관 PDF는 직접 열기에서 404가 발생해 현재 국가 제한을 확정하지 않았다.

5. 국내·글로벌 UX 제안

회원 국적·화면 언어·접속 위치를 같은 것으로 취급하지 않는다. 언어는 표시 설정으로 유지하고, 결제 국가/지역을 확인해 가능한 수단을 안내한다. 자동 추정은 초기 추천에만 사용하고 사용자가 변경할 수 있게 한다. 서버가 국가·가맹점·통화·상품·운영 상태를 검증한다.

6. 권고하는 진행 순서

  1. 메일·PortOne·PayPal 콘솔에서 사업자 심사, 보완 요청, 운영 채널과 계정 국가를 확인한다.

  3. 서버의 가용성·사용자 권한·테스트 환경 격리와 운영 개방 스위치를 정한다.
  4. 국내·글로벌 화면 및 실패/복구 흐름을 구현하고 반대 공급자의 독립 리뷰를 받는다.
  5. 별도 테스트 환경에서 결제→검증→한 번만 적립→재조회→취소/환불을 검증한다.
  6. 확인된 운영 설정과 배포안을 승인받은 뒤 개방한다. 가상화폐는 이 경로와 병렬로 조건을 조사하되 후속 단계로 도입한다.
