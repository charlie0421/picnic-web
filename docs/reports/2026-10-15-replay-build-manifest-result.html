Replay 배포 빌드용 CSS manifest 결과

이 결과는 시험 harness 안의 검증이다. 제품 코드에 연결하지 않았고 운영 Sentry Replay를 활성화하지 않았다. production 사이트에서는 공개 자산만 읽었고 녹화하지 않았다. 브랜치 feat/replay-build-manifest는 push하지 않았다.

요약: 실제 글꼴을 쓰는 production 설정 빌드에서 생성기가 통과했다. 이것이 완료 기준이다. 이 빌드의 CSS 자산 2개는 production(https://www.picnic.fan/ko/vote)과 바이트 단위로 같고, production 대조 도구가 통과했다. 계약은 manifest의 출력 텍스트만 내보내며 글꼴 URL을 출력하지 않는다. raw 복원과 투영 복원의 차이는 0이다. WebKit·Firefox 녹화는 정확 비교에서 맞지 않아 segment 0에서 종료한다(측정만 함). 교차 공급자 리뷰(Codex)는 Important 3건을 지적했다. 모두 고쳤고, 재검증에서 남은 1건(HTML 정규식 추출)도 고쳤다. 이 마지막 수정은 아직 교차 재검증을 받지 않았다(§10). 서로 다른 두 로컬 빌드에서 만든 manifest의 내용이 같다(§3.4).

4. production 대조

check-production-css.cjs가 https://www.picnic.fan/ko/vote에 대해 통과했다(ok: true, 2026-10-15 21:06 KST). 리뷰 수정 뒤의 도구(모든 stylesheet·script를 origin과 함께 비교)로 다시 실행해도 통과했다. production HTML에는 다른 origin의 stylesheet·script와 inline <style>이 없다.

  • production이 제공하는 link CSS 2개의 이름과 sha256이 manifest의 sourceSha256과 같다.
  • production이 참조하는 JS chunk 36개에서 styled-jsx 원문 7개를 도출했고, manifest의 styled-jsx 3개가 모두 그 안에 있다.
  • viewport가 같다.
  • production BUILD_ID는 dWn6qfDz7qrUbY4zRGawM였다. 같은 날 #136 merge(11:25) 전에는 nGXugIVZRSFy4ga95YQAZ였다(merge 뒤 새 배포). 로컬 빌드는 ulGwme5ItIoLQx4aLUchX다. BUILD_ID가 셋 모두 다르지만 CSS는 같다. 따라서 BUILD_ID 대신 내용에 결합하면 배포마다 manifest를 다시 만들 필요가 없다는 것을 확인했다.

7. spec·계획과 다르게 구현한 점

  • hover 제거: spec §5 단계 7은 hover를 허용 분류로 적었다. 구현은 캡처가 측정 전에 pointer를 화면 밖으로 옮겨 hover를 없애고, 분류에서 hover를 뺐다. 이전 증거에서 hover와 svg placeholder가 겹친 6px 차이를 규칙으로 분류할 수 없었기 때문이다(계획 단계 결정). spec보다 엄격하다.
  • compare-engine-css는 .ts다. TS 계약을 그대로 실행하려고 tsx로 실행한다.
  • 서버 도구를 네 파일로 나눴다: net-guard.cjs, font-mock.cjs, vote-list-upstream.cjs, vote-list-server.cjs.
  • production 대조의 styled-jsx 비교: production chunk에서 도출한 원문을 Chromium으로 CSSOM 텍스트로 바꾼 뒤 accept와 비교한다.
  • fixture README 갱신: 계획의 파일 목록에 없었지만, 옛 fixture를 설명하던 fixtures/vote-list/README.txt를 새 빌드·도구·절차로 갱신했다.

8. 남는 위험

  • 빌드 사이에 Google Fonts 응답이 바뀌면 글꼴 CSS가 달라져 production 대조가 실패한다(fail-closed). 이번에는 로컬과 production이 같았다. next/font/local로 바꾸면 이 위험이 없어진다(제품 변경, 제안만).
  • Chromium 버전이 바뀌어 CSSOM 직렬화가 달라지면 같은 빌드라도 종료한다. 이번 측정은 Playwright 1.63.0의 Chromium 한 버전이다.
  • WebKit·Firefox 녹화는 종료한다(§6). 실제 사용자 중 이 엔진의 비율만큼 Replay가 남지 않는다.
  • 재생 화면은 fallback 글꼴로 그려진다. 측정한 영향은 필터 칩의 폭과 x 위치(최대 36px)다. 재생하는 컴퓨터에 Inter가 설치되어 있으면 그 글꼴이 쓰인다.
  • 기존 위험은 그대로다: 마스킹한 text의 길이·위치, class 조합, placeholder 치수가 화면 구조를 남긴다. 배너 상한이 P0 설계보다 느슨하다. SDK 내부 메모리·재시도의 한계가 있다.
  • fixture wire-*.bin은 원본 SDK envelope다. 마스킹하지 않은 custom event와 loopback 글꼴 URL이 들어 있다(합성 데이터). 저장소 밖으로 보내지 않는다.

9. 검증하지 않은 범위

  • 실제 iOS Safari, 실제 데스크톱 Safari·Firefox, Playwright 1.63.0 밖의 Chromium 버전.
  • manifest를 제품 번들에 넣는 일, 런타임 origin 설정, CI·배포 관문 자동화(후보 C).
  • 운영 Sentry 저장과 대시보드 재생.
  • upcoming·completed 목록, 더보기, filter, API 오류, popup, 로그인 사용자, 다른 route(후보 A).
  • BFCache 실측 복귀와 실제 background timer 지연(P0 미검증 항목과 같다).

10.2 1차 리뷰 (Codex)

판정: REQUEST_CHANGES. Important 3건. manifest 출력 경로(snapshot·add·style text·link 변경)와 복원 분류에는 막을 문제가 없다고 판단했다.

심각도지적처리
Important차단기가 fetch의 첫 URL만 검사한다. redirect 대상, undici 직접 호출, Next의 Edge fetch가 다른 호스트에 닿는다.고침(3d4fdd2e). 검사 지점을 net.Socket.prototype.connect로 옮겼다. 모든 TCP·TLS 클라이언트가 이곳에서 소켓을 연다. DNS 조회 전에 막는다.
Importanthttp.request(url, {hostname})처럼 옵션이 덮어쓴 호스트를 검사하지 않는다.고침(3d4fdd2e). 같은 수정으로 병합된 최종 목적지를 검사한다.
Importantproduction 대조가 해시 이름의 경로 문자열만 찾는다. 다른 origin의 stylesheet나 추가 stylesheet가 있어도 통과한다.고침(3d4fdd2e). 모든 rel=stylesheet link와 script src를 페이지 기준으로 해석하고, 다른 origin과 inline <style>을 거부하고, 집합 전체를 비교한다.

각 수정은 실패하는 시험을 먼저 확인했다. 차단기 시험은 차단기를 preload한 자식 프로세스에서 http·https 옵션 덮어쓰기, fetch redirect, undici.fetch, net.connect, tls.connect를 시도한다. 수정 전에는 httpOverride가 DNS 조회(ENOTFOUND)까지 갔다. 수정 뒤에는 모두 replay-harness-network-blocked로 끝나고 loopback만 통과한다. NODE_OPTIONS preload는 worker thread와 자식 프로세스에도 적용됨을 확인했다.
