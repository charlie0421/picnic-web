Replay 배포 빌드용 CSS manifest 설계

작성: 2026-10-15 KST · 기준 HEAD 8b6d5b3a · 선행 문서: 투표 목록 계약 설계, 투표 목록 계약 결과, 투표 목록 계약 핸드오프 §5 후보 B

목표: 실제 배포 빌드에서 쓸 수 있는 투표 목록 CSS manifest를 만든다. 빌드마다 manifest를 생성·검토하는 절차와 실제 글꼴 CSS(url(, @font-face) 규칙을 정한다. 완료 기준: 실제 배포 빌드에서 생성기가 통과한다. 통과할 수 없으면 그 이유를 문서로 남긴다.

이 문서는 제품 연결·운영 활성화의 승인이 아니다. 제품 app/·components/·lib/는 바꾸지 않는다. 모든 코드는 scripts/replay-p0/ 아래에 둔다.

1. 범위와 전제

포함manifest v2 형식. 계약의 CSS 처리 변경(origin 정규화, manifest 출력, BUILD_ID 결합 제거). 실제 글꼴 규칙. 빌드·캡처·생성·production 동등성 확인·엔진 비교 도구. 실제 글꼴 빌드의 fixture·manifest로 교체. 빌드마다 절차. WebKit·Firefox 직렬화 측정.
제외제품 번들에 manifest 포함, 런타임 origin 설정, CI·배포 관문 자동화, 운영 활성화(후보 C). WebKit·Firefox 지원. upcoming 등 다른 화면과 상태(후보 A). next/font/local 전환(제품 변경). production 사이트에서의 녹화.
유지투표 목록 계약의 tag·속성·inline style·class token·rrweb 이벤트 규칙. 엔진과 예산. P0 계약(contracts/p0-fixture.ts).

전제 (2026-10-15 사용자 확인):

  • “실제 배포 빌드”는 production과 같은 설정(실제 글꼴, font mock 없음)으로 로컬에서 만든 빌드다. 그 CSS 자산이 production 공개 자산과 sha256으로 같으면 manifest를 production에 적용할 수 있다고 본다. production 사이트에서는 녹화하지 않는다.
  • 작업은 scripts/replay-p0/ harness 안에서 끝난다.
  • 계약은 개인정보 경계다. 이 변경은 고위험으로 분류한다.
  • WebKit·Firefox는 측정만 한다. manifest 형식은 엔진별 입력을 여러 개 받을 수 있게 하지만, 생성과 검증은 Chromium만 한다.

3. manifest v2와 계약

3.1 manifest 형식

{
  "version": 2,
  "generatedFrom": { "buildId": "…", "origin": "http://127.0.0.1:53931", "commit": "…" },
  "sdkVersion": "9.47.1", "release": "…", "environment": "…",
  "viewport": "…", "announcerStyle": "…",
  "linkCss": [{ "asset": "/_next/static/css/….css", "sourceSha256": "…",
                "accept": [{ "engine": "chromium", "sha256": "…", "text": "…" }],
                "output": { "sha256": "…", "text": "…" } }],
  "styleText": [{ "accept": [{ "engine": "chromium", "sha256": "…", "text": "…" }],
                  "output": { "sha256": "…", "text": "…" } }],
  "classes": ["…"], "statusColors": ["…"]
}
  • accept: 계약이 입력으로 허용하는 텍스트다. origin을 정규화한 값이다(§3.3). 엔진별로 여러 개 둘 수 있다. 이 작업은 chromium 하나만 만든다.
  • output: 계약이 출력하는 텍스트다. 계약은 wire 문자열을 출력하지 않는다.
  • generatedFrom: manifest를 만든 로컬 빌드의 BUILD_ID, origin, commit이다. 기록용이다. 계약은 이 값을 비교하지 않는다.
  • classes: 모든 output 텍스트의 class 선택자에서 추출한다.
  • 같은 목록(linkCss 또는 styleText) 안의 두 항목에 같은 accept 텍스트가 있으면 생성기는 실패하고 계약은 생성할 때 거부한다.
  • build-css-manifest.cjs --previous는 v1과 v2 manifest를 모두 읽는다. v1의 wire는 v2의 accept 텍스트와 비교한다.

3.2 계약 옵션

createVoteListContract({ manifest, origin, bannerCount })

  • manifest.version이 2가 아니면 계약 생성을 거부한다.
  • origin은 ^https?://[a-z0-9.-]+(:[0-9]{1,5})?$ 형식만 받는다. 다른 값이면 계약 생성을 거부한다.
  • buildId 옵션과 BUILD_ID 일치 검사를 없앤다.
  • bannerCount 규칙은 바꾸지 않는다.

3.3 입력 정규화와 식별

  1. 계약은 link _cssText와 style text에서 url("<origin>/를 모두 url("/로 바꾼다.
  2. 계약은 바꾼 텍스트와 정확히 같은 accept 텍스트를 가진 항목을 찾는다. link는 linkCss에서, style text는 styleText에서 찾는다.
  3. 항목이 없으면 계약은 schema로 종료한다.
  4. 항목이 있으면 계약은 그 항목의 output 텍스트를 출력한다.

정규화는 비교에만 쓴다. 출력은 manifest의 텍스트이므로 wire의 내용은 출력에 들어가지 않는다. head 정적 노드의 attribute·text 변경은 지금처럼 종료한다.

3.4 글꼴 규칙 (생성기)

생성기는 빌드 CSS를 생성 CSSStyleSheet로 파싱하고 CSSOM 규칙 단위로 검사한다.

규칙처리
@import생성 실패.
@font-face, src가 url()만 사용모든 URL 경로가 ^/_next/static/media/[0-9a-f]{16}(-s)?(\.p)?\.woff2$와 같고, 각 URL에 format("woff2")가 붙어야 한다. 아니면 생성 실패. 통과한 규칙은 output에서 뺀다.
@font-face, src가 local()만 사용output에 남긴다.
@font-face, url()과 local()을 함께 사용생성 실패.
그 밖의 규칙에 url(생성 실패(지금과 같다).
  • accept는 빌드 CSSOM 전체에 SDK 호환성 변환을 적용한 값이다. 지금처럼 live CSSOM 값, 정규화한 wire 값과 같아야 한다.
  • output은 남긴 규칙의 CSSOM 텍스트에 SDK 호환성 변환을 적용한 값이다. output에 url(이 있으면 생성 실패.
  • 재생 화면에는 Inter의 @font-face가 없다. 따라서 font-family: Inter, Inter Fallback은 Inter Fallback(Arial과 metric override)으로 그려진다. 단, 재생하는 컴퓨터에 Inter가 설치되어 있으면 그 글꼴이 쓰인다.

3.5 빌드 결합

  • manifest는 BUILD_ID가 아니라 내용에 결합한다. 계약은 CSS를 정확히 비교하므로 CSS가 같은 빌드는 같은 manifest를 쓴다.
  • CSS 밖의 값(viewport, announcer style, 상태색)이 바뀌면 계약은 지금처럼 종료한다(fail-closed).
  • 이유: BUILD_ID는 CSS가 같아도 배포마다 바뀐다. BUILD_ID 결합은 안전성을 더하지 않고 배포마다 재생성만 강제한다.

5. 검증과 완료 기준

각 단계를 통과해야 다음 단계를 진행한다.

  1. 계약 단위 시험(TDD). origin이 같으면 통과하고, 다른 origin(예: https://evil.example)이면 schema로 종료한다. 잘못된 origin 옵션과 v1 manifest는 계약 생성을 거부한다. 출력은 wire가 아니라 output 텍스트이고, 글꼴 시트 출력에 url(이 없다. 기존 PIIMARK 시험을 유지한다. P0 단위 시험 139개는 결과가 바뀌지 않는다.
  2. 생성기 단위 시험. 허용 경로·woff2의 @font-face는 output에서 빠진다. 다른 경로, 외부 호스트, data:, 다른 format, url()과 local() 혼용, @font-face 밖의 url(, @import는 생성 실패다. 기존 CSSOM 주입 음성 시험을 유지한다.
  3. 실제 글꼴 빌드 통과 (완료 기준). 실제 글꼴 빌드에서 생성기가 v2 manifest를 만든다. 예상 검토 요약: 글꼴 시트와 font class만 바뀌고 Tailwind CSS와 styled-jsx는 그대로다.
  4. production 동등성. check-production-css.cjs가 https://www.picnic.fan/ko/vote에 대해 통과한다. link CSS 2개의 sha256, styled-jsx 도출, viewport가 같아야 한다. 실패하면 원인을 기록한다(예: 빌드 사이의 Google Fonts 변경). 이 기록도 완료 기준의 “통과할 수 없는 이유”다.
  5. 새 캡처 투입. 1280·390px, 압축·비압축에서 segment 0→1→2가 통과한다. Meta href https://replay.invalid/ko/vote를 뺀 출력 bytes에서 capture.test.ts의 FORBIDDEN 문자열과 url(, /_next/static/media, .woff2가 0회다.
  6. 변조 반례. 새 반례: 글꼴 CSS의 origin 변경, url()을 쓰는 @font-face 추가, 글꼴 CSS 1byte 변경. 모두 schema로 종료한다. 기존 반례 8종을 유지한다.
  7. 복원 비교. raw 복원과 투영 복원의 상자 차이가 두 폭 모두 0이다(네트워크 차단). 투영 복원과 원본 대조군의 차이는 기존 분류(media·hover·svg placeholder)에만 있다. 원본 (2)와 대조군의 차이는 글꼴 영향으로 기록만 한다(관문이 아니다).
  8. 엔진 측정 (기록만). WebKit·Firefox 캡처에 대해 시트별 일치 여부, 다른 규칙 수와 예시, 계약의 종료 reason을 기록한다.
  9. 전체 회귀. npx vitest run __tests__/scripts/replay-p0(TZ=UTC 포함), npm test, npx tsc --noEmit --incremental false, 범위 ESLint, 브라우저 22개 케이스, git diff --check.

완료: 1–7과 9가 통과하고 8을 기록한다. 반대 공급자 Frontier 리뷰(Codex gpt-6.1-sol/high)가 APPROVE한다. 결과는 docs/reports/의 결과 보고서 HTML로 남긴다. 승인한 설계 안에서 3이나 4를 통과할 수 없으면 계약을 넓히지 않는다. 멈추고 이유를 문서로 남긴다.

6. 빌드마다 절차

6.1 재생성 조건

다음 중 하나라도 바뀌면 manifest를 다시 만든다.

  • /ko/vote가 쓰는 link CSS 자산(이름·sha256)
  • styled-jsx text
  • @sentry-internal/replay·styled-jsx·Next 버전
  • viewport meta, 상태색 상수(VoteStatusFilter.tsx)

배포 뒤 check-production-css.cjs를 실행해 변화를 감지한다. 이 작업에서는 수동으로 실행한다. 자동화는 후보 C에서 한다. 실패하면 그 배포에는 manifest가 맞지 않는다. 후보 C에서는 그 배포의 Replay를 꺼진 상태로 둔다(fail-closed).

6.2 절차

  1. 워크트리에서 vote-list-server.cjs로 빌드하고 서빙한다.
  2. vote-list-capture.cjs --browser chromium으로 캡처한다.
  3. build-css-manifest.cjs --previous <현재 manifest>로 manifest와 검토 요약을 만든다.
  4. 검토 요약을 검토한다(§6.3).
  5. fixture와 시험 기대값을 갱신하고 전체 회귀를 통과시킨다.
  6. PR 본문에 검토 요약을 붙이고 merge한다.
  7. 배포 뒤 check-production-css.cjs로 production과 대조한다.

6.3 검토 기준

  • 자동 검사: 생성기의 실패 조건이 자동 검사다. 생성기가 실패하면 manifest를 만들지 않는다.
  • 사람 검토: 새 class token이 사용자 데이터처럼 보이면 거부한다(예: 긴 숫자열, 이메일, 사람 이름). 새 CSS 자산과 뺀 글꼴 URL 수를 빌드 변경으로 설명할 수 없으면 거부한다.

7. 남는 위험

  • 빌드 사이에 Google Fonts 응답이 바뀌면 글꼴 CSS가 달라진다. 그러면 production 동등성 확인이 실패한다(fail-closed). next/font/local로 바꾸면 이 위험이 없어진다. 제품 변경이므로 제안만 한다.
  • Chromium 버전이 바뀌어 CSSOM 직렬화가 달라지면 같은 빌드라도 계약이 종료한다. 이 작업은 설치된 Playwright Chromium 한 버전만 측정한다.
  • 재생 화면은 fallback 글꼴로 그려진다. 재생하는 컴퓨터에 Inter가 설치되어 있으면 그 글꼴이 쓰인다. 글꼴 영향은 측정값으로 남긴다.
  • Safari·Firefox 사용자의 녹화는 맞지 않을 가능성이 높다. 이 작업은 측정만 하고 지원하지 않는다. 실제 iOS Safari는 측정하지 않는다.
  • 기존 위험은 그대로다: 마스킹한 text의 길이·위치, class 조합, placeholder 치수가 화면 구조를 남긴다. 배너 상한이 P0 설계보다 느슨하다. SDK 내부 메모리·재시도의 한계가 있다.
  • fixture는 원본 SDK envelope다. 마스킹하지 않은 custom event(합성 데이터의 URL·aria-label)가 있다. 저장소 밖으로 보내지 않는다.
