목표: 사용자가 별도로 동의한 경우에만 공개 투표 목록의 화면 배치·배너·스크롤 문제를 최대 60초 동안 재현한다.

구조: 기존 Sentry 클라이언트와 일반 오류 전송을 유지한다. 문서 단위 동의 상태, 수동 SDK 연결, 매 전송의 서버 자격 검사, 별도 HTTPS 전송을 추가한다. 기존 loopback 시험 경로와 운영 경로를 분리하고 화면 변환 엔진만 재사용한다.

설계: 수동 동의 진단 설계. 사용자의 이번 “진행”으로 설계 승인을 받았다. 기준 커밋은 d89b97fe다.

공통 제약

  • 운영 주소는 정확히 https://www.picnic.fan/ko/vote다. 빈 ?·#까지 거부한다. 직접 연 새 문서의 초기 목록과 PC Chrome만 허용한다. 모바일·Edge·Safari·Firefox·HeadlessChrome·식별 불명은 거부한다.
  • 클라이언트 비로그인, 서버의 빈 Cookie 또는 허용된 locale 쿠키 1개, Authorization 부재, 광고 denied, 광고 로드 이력 없음이 모두 필요하다. Supabase 인증 동작·DB·스키마는 변경하지 않는다.
  • 동의는 메모리에만 두고 자동 session/on-error 샘플링은 모두 0이다. 동의 전 integration·recorder·버퍼는 생성하지 않는다. 안내 열기·취소는 시작 시도를 소비하지 않는다. 문서당 시작 시도는 1회이며 CLOSED는 되돌리지 않는다.
  • 실제 recorder 시작부터 60_000 ms, 단조 시계 performance.now()를 사용한다. 누적 전송 시도량은 직렬화된 변환 envelope 기준 8 * 1024 * 1024 bytes다. 동시 전송 1개, 재시도 0회다.
  • Worker 2_000 ms, 서버 자격 검사 1_000 ms, 실제 POST 5_000 ms를 각각 적용한다. 중지·60초 만료는 각 타이머보다 우선한다. 실패·취소 후 누적 바이트를 돌려주지 않는다.
  • 포인터·휠 스크롤·배너 버튼만 허용한다. 배너의 Enter/Space 외 키 입력, 다른 클릭·입력, 추가 목록·팝업, 경로·광고·인증 변화, 숨김·resize·BFCache 복귀는 종료한다. 원래 사용자 동작은 취소하지 않는다.
  • 첫 POST 전에 실제 SDK의 32자리 소문자 16진수 Replay ID를 화면에 표시한다. 표시 전 envelope 도착, 잘못된 ID, 표시 ID와 envelope ID 불일치는 종료한다. 별도 ID 매핑·ID 영속 저장은 만들지 않는다.
  • payload는 허용된 구조와 스타일로 새로 만든다. 모든 글자·입력을 가리고 미디어를 차단한다. 실제 URL·query·계정·원본 오류·콘솔·네트워크 내용은 보내지 않는다. 가상 주소는 https://replay.invalid/ko/vote다. 일반 오류의 Replay 연계 필드 제거를 유지한다.
  • 기본 서버 스위치는 OFF다. 최종 빌드와 manifest의 검증 표식이 없거나 다르면 UI도 OFF다. 운영 활성화·Sentry 설정 변경·개인정보처리방침 수정·실제 데이터 삭제는 이 구현 계획의 실행 승인에 포함하지 않는다.
  • 자동 보관 ≤90일 확인, 조사 종료 다음 영업일까지 또는 수집 후 7일 이내 수동 삭제, 담당자 Charlie, 실제 삭제 요청 경로·고지는 공개 활성화 조건이다. PayPal·PortOne 보류와 Jira 현재 상태를 유지한다.

작업 1. 배포 파일과 화면 변환 규칙 묶기

쉽게: 녹화기가 이해하는 화면 규칙이 실제 서비스 화면과 같다는 증거를 빌드마다 만든다. 증거가 없으면 버튼을 숨긴다.

파일: 위 build·verify-build·diagnostic-build 파일을 생성한다. 기존 scripts/replay-p0/tools/build-css-manifest.cjs의 CSS 추출·검사 함수를 재사용한다. 생성 후보는 lib/sentry/replay/generated/diagnostic-manifest.json, 기본 무효 표식은 lib/sentry/replay/generated/diagnostic-proof.json에 둔다. manifest는 CSS 템플릿으로 Git에 포함하고 빌드별 proof는 생성 캐시로 제외한다. 템플릿에는 release·environment를 넣지 않으며 generatedFrom.commit은 생성 출처 참고값일 뿐 일치 조건이 아니다. sourceStyleSha256: string[]에 빌드 전체에서 추출한 styled-jsx 원문 해시를 중복 제거하고 정렬한 목록을 기록한다. next.config.js에 해당 API의 정확한 proof·.next/BUILD_ID 파일 추적 경로를 추가한다.

인터페이스: diagnostic-build.ts는 server-only이며 파일을 읽는 Node 런타임에서만 사용한다. 브라우저에는 전체 proof를 보내지 않는다.

CSSOM 변형의 허용 여부는 후보 생성 및 실제 Chrome 시험에서 검증한다. 원문 해시 범위는 투표 경로에 한정하지 않고 빌드 전체다. 따라서 다른 화면의 스타일 변경도 proof를 무효화할 수 있으며, 활성화 빌드에는 템플릿을 갱신해야 한다. 빌드 직전에 proof를 {"version":1,"verified":false}로 덮고, 빌드 후 CSS·스타일 원문·SDK·commit·release·environment·BUILD_ID가 모두 맞을 때만 유효 proof를 rename으로 쓴다. next build 자체 실패는 항상 non-zero다. 대조 실패는 무효 proof와 경고를 남기며, 서버 REPLAY_DIAGNOSTIC_ENABLED=1 또는 REPLAY_DIAGNOSTIC_REQUIRE_PROOF=1이면 non-zero, 둘 다 아니면 exit 0으로 진단 OFF 배포를 허용한다. 활성화 배포에서 REQUIRE_PROOF를 꺼도 엄격 검증을 우회하지 못한다. 재빌드는 같은 무효화·대조를 다시 수행한다.

Vercel이 최종 build 명령 이후 proof를 패키징하도록 명시적으로 추적한다. 파일 읽기 실패 시 null로 닫는다. standalone 출력은 현재 사용하지 않으며, 향후 사용 시 최종 proof 복사·대조를 별도 추가해야 한다.
