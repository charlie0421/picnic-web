Replay 제한 수집 핸드오프

작성: 2026-10-15 02:01 KST · 독자: 다음 세션의 조정자 · 범위: picnic-web의 격리된 Replay P0와 제품 녹화 형식 조사

P0 구현·로컬 검증과 production 형식 조사를 완료했다. 다음 작업은 제품용 DOM/CSS 허용 계약을 구체화하고, 그 계약으로 로컬 재생을 검증하는 단계다. 현재 P0를 제품에 바로 연결하면 schema로 종료된다.

제품 연결과 운영 활성화는 완료되지 않았다. 최근 작업은 합성 데이터·loopback 수신기를 사용했다. 새 Replay 수집 경로의 외부 Sentry 저장과 대시보드 재생은 확인하지 않았다. 기존 오류·성능 이벤트의 운영 점검과 이 상태를 혼동하지 않는다.

  4. 필요한 구현과 검증을 기존 승인 범위에서 진행한다. 제품 연결·인증/광고 상태 통합·운영 활성화는 별도 범위다. 대규모 구조 변경 전에는 사용자 지침대로 구체적인 계획을 확인한다.

4. 현재 P0의 경계

  • 코드는 scripts/replay-p0/, 단위 시험은 __tests__/scripts/replay-p0/에 있다. 제품 app/components/lib에서 P0를 호출하지 않는다.
  • controller.ts는 WAITING→LOADING→ARMED→RECORDING→CLOSED 상태와 세대를 관리한다. 같은 document의 CLOSED는 되돌리지 않는다.
  • projection.ts는 합성 fixture 전용이다. tag 7개·class 4개·고정 CSS, 좁은 inline style만 허용한다. 제품 범용 decoder가 아니다.
  • transport.ts와 Worker 경계는 전송 직전 상태/세대를 재검사한다. 예외·순서 위반·예산 초과는 종료한다.
  • correlation.ts는 일반 이벤트의 Replay 연결 식별자를 제거한다. P0의 tracePropagationTargets=[]는 유지한다. 기존 span의 frozen DSC 때문에 헤더 전파를 켜면 별도 검증이 필요하다.
  • 입력·해제·출력 각 8 MiB, 깊이 80, 순회 값 200,000, 이벤트 10,000, 보관 노드와 tombstone 합계 20,000 제한이다. Worker 2초·fetch 5초·녹화 5분 제한은 main event loop가 실행될 때 처리된다.
  • SDK 내부 무한 processor/Worker 대기는 유한 정리를 보장하지 못한다. 공개 SDK start를 직접 호출하면 메모리 녹화를 재시작할 수 있지만 닫힌 전송 관문은 새 요청을 막는다. 원본 메모리의 물리적 삭제나 SDK 모든 자원의 해제를 보장하지 않는다.

처음 제품 적용 후보는 정확한 /ko/vote, 빈 query/fragment, 인증 초기화 완료·익명 확인, 광고 미동의 확정·해당 document에서 광고 SDK 미실행 상태다. canLoadAds=false만으로 충족했다고 판단하지 않는다. 광고 동의와 Replay 수집 근거·동의는 별개다.

6. 권장 후속 순서와 완료 기준

  1. 제품 계약: CSS manifest, typed DOM/head/shadow, 고정 class·상태 enum·수치 style·소수 placeholder 규칙을 정한다. 자유 URL/문자열을 관측했다는 이유로 허용하지 않는다.
  2. 로컬 구현과 반례: 제품용 변환기를 구현하고 snapshot·mutation·CSS·metadata·custom event·압축/비압축의 민감 문자열과 잘못된 형식·순서·예산을 시험한다. 기존 P0 종료 관문을 약화하지 않는다.
  3. 제품 화면 복원: 합성 데이터·고정 시각/폰트로 실제 컴포넌트 시나리오를 넓힌다. 설계 기준은 주요 위치/크기 차이 1 CSS px 이내, opacity 0.01 이내, 상태·개수·배너 인덱스 일치다. 의도한 마스킹·미디어·폰트 차이만 예외로 기록한다.
  4. 실제 상태 연결: 인증·동의·navigation 변경이 React 반영 또는 외부 script 삽입 전에 관문을 닫는지 검증한다. 변경 후 effect/observer만으로 종료하는 구현은 설계 조건을 만족하지 않는다.
  5. 별도 외부 검증과 운영 결정: 최종 outgoing envelope와 저장 segment, 같은 Replay ID의 실제 대시보드 재생을 비교한다. 운영 수집 근거·기간·샘플링·보관·중단 책임을 별도로 정한다.

사용자는 이번 메시지에서 핸드오프 문서 작성을 요청했다. 이 문서 자체는 새 구현·인증 변경·배포·외부 저장·push/merge의 승인이 아니다. 기존에 승인된 작업을 불필요하게 다시 확인하지 않되, 새 단계의 승인 범위를 이전 P0 승인과 혼동하지 않는다.

10. 다른 세션의 운영 후속 작업

로컬 main의 docs/handoff-2026-10-14.html에는 별도 세션의 결과가 있다. 이 문서는 그 기록을 요약하며 현재 원격 상태를 다시 조회한 결과는 아니다.

  • 사용자가 Sentry의 Prevent Storing of IP Addresses를 켰다는 기록이 #133으로 반영됐다. 새 이벤트에서 IP가 비었는지 확인하는 작업은 별도로 남아 있다.
  • #73/#74는 실제 운영 서버 이벤트의 redaction·도착 증거를 기다리는 상태로 기록돼 있다. 확인을 위해 운영 오류를 일부러 만들지 않는다.
  • Sentry 7E/7F, Data Scrubber의 다른 설정·과거 이벤트 삭제, #75~#77, 로그인 smoke 등은 그 세션의 별도 후속 목록이다. 이번 Replay P0 완료로 닫지 않는다.
  • Jira의 검토중/완료 상태를 임의로 바꾸지 않는다. push/merge/배포는 해당 변경의 승인 범위와 최신 Git 정책을 확인한다.

문서 작성 요청에 따라 핸드오프만 생성했다. 실제 다른 에이전트나 터미널에 작업 소유권을 넘기지 않았다.
