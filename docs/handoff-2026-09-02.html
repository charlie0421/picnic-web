한 줄 요약. 지난 세션이 남긴 숙제 “Sentry 가 정말 동작하는가”를 확인하는 작업이었다. 답은 서버 파이프라인은 정상이었고, 에러가 안 보인 건 조직 쿼터가 picnic-app 버그 하나에 전부 타버렸기 때문이었다. 그 버그의 수정 효과까지 대조 데이터로 확정했고, picnic-web 이 리플레이 쿼터를 태우던 설정 오류도 잡았다. 코드 커밋은 0건 — 전부 설정과 관측의 문제였다.

가장 중요한 것 하나. 이번 세션에서 내가 확신을 갖고 말한 판단 3건이 틀렸다. 셋 다 원인이 같다 — 관측되지 않는 것을 “없는 것”으로, 도구의 동작을 “아는 것”으로 단정했다. 다행히 2건은 실행 직전 재검증으로 막았지만 1건은 사용자에게 잘못 보고한 뒤 정정했다. 자세한 건 §4를 반드시 읽어라.

3. 원인 규명 — 왜 에러가 하나도 안 보였나

지난 핸드오프 §7의 “Sentry 대시보드에서 서버 이벤트 수신 확인” 항목에 대한 답이다.

서버 파이프라인은 처음부터 정상이었다

리플레이 쿼터를 태운 건 picnic-web 이었다

코드(instrumentation-client.ts:10)의 프로덕션 기본값은 replaysSessionSampleRate = 0.0 인데, Vercel 환경변수가 1.0 으로 덮어쓰고 있었다(486일 전 설정). 방문자 전원 녹화라 50건 한도가 하루면 터진다.

코드의 기본값을 믿지 마라. process.env.X || 기본값 패턴은 환경변수가 있으면 기본값이 죽는다. 실제 값은 npx vercel env pull 로 확인해야 한다.

4. 값을 치르고 배운 것 — 내가 틀린 판단 3건

#내가 한 말왜 틀렸나결과
1 “5G9 는 8/20 이후 0건이니 이미 패치로 잡혔다” 0건이 된 건 수정이 아니라 쿼터 소진이었다. 같은 시각 rate_limited 가 0 → 781 로 튀는 걸 안 봤다. 앱은 계속 보내고 있었다 사용자에게 잘못 보고 후 정정
2 “5GQ 를 뮤트하면 예산 여유가 생긴다” Sentry 아카이브는 이벤트를 여전히 수집·과금하고 이슈 스트림에서만 숨긴다. 쿼터와 무관하다 실행 시점에 자체 발견해 정정
3 “5G9 해제를 1.3.1+130104 로 재지정하자” Sentry 는 해제 릴리스보다 다음 릴리스에서 발생해야 regression 으로 잡는다. 130104 로 바꾸면 정작 감시 대상인 130104 자체의 재발을 놓친다 실행 직전 재검증으로 차단

공통 원인: 1번은 관측되지 않는 것을 “없는 것”으로 읽었고, 2·3번은 도구(Sentry)의 동작을 확인 없이 “아는 것”으로 단정했다. 지난 핸드오프 §3이 “코드에서 추측했다”였는데, 이번엔 대상이 플랫폼 동작으로 바뀌었을 뿐 같은 실패다.

효과가 있었던 습관: 상태를 바꾸는 API 를 호출하기 직전에 “이 설정이 정확히 무엇을 하는가”를 한 번 더 확인한 것. 3번은 그 한 번의 확인으로 막혔다. 쓰기 직전 재확인을 규칙으로 유지할 것.

5. 반드시 알고 있어야 할 것

Sentry 쿼터는 카테고리별로 따로 걸린다

errors 가 터져도 spans/transactions 는 계속 들어온다. 이번에 “서버 SDK 가 살아 있다”를 증명한 게 정확히 이 트랜잭션 데이터다. 에러가 안 보인다고 파이프라인이 죽은 게 아니다.

또한 쿼터 초과 상태에서도 outcome 통계(stats_v2)는 계속 집계된다. 이벤트 내용은 못 봐도 “몇 건이 왔다가 버려졌는지”는 알 수 있다. 이게 §4-1을 정정할 수 있었던 근거다.

resolved in release 의 의미론

해제 릴리스 X 로 마크된 이슈
  → X 보다 "다음" 릴리스에서 발생해야 regression
  → X 자신 또는 X 이전 릴리스의 이벤트는 조용히 흡수

현재 5G9 는 1.3.0+130007 로 해제돼 있다. 이게 의도한 설정이다: 1.3.0 꼬리(하루 수백 건)는 알림 없이 흡수되고, 1.3.1+130104 이상에서 1건이라도 나오면 regression 알림이 뜬다. 바꾸지 마라.

아카이브(ignore)는 비용을 줄이지 않는다

쿼터를 실제로 아끼려면 클라이언트에서 보내지 않게 해야 한다. Sentry 쪽 조치는 스트림 정리·알림 억제 효과만 있다.

키별 rate limit 은 Team 플랜에서 안 된다

API 가 200 을 반환하면서 값을 조용히 무시한다(rateLimit: null 유지). Business 플랜 기능이다. 현재 조직의 폭주 방어선은 Spike Protection(작동 중, 지난 폭주 때 2,937건 차단)과 PAYG 금액 상한 둘뿐이다.

10. 함정

NEXT_PUBLIC_* 변경은 재배포해야 반영된다. 빌드 시 번들에 인라인되므로 vercel env 만 바꾸면 아무 일도 안 일어난다. 확인법은 번들에서 parseFloat("...") 를 직접 grep 하는 것.

Vercel CLI 로는 기존 환경변수 값을 못 바꾼다. vercel env add 는 “이미 모든 환경에 존재한다”며 거부하고, rm → add 조합은 이 세션에서 조용히 실패했다. REST API 로 PATCH 하는 게 확실하다(항목 ID 유지, target 유지).

같은 이름의 환경변수가 target 별로 여러 항목일 수 있다. 이 레포는 development 용과 preview+production 용이 별도 항목으로 존재한다. 하나만 고치면 절반만 바뀐다.

zsh 에서 --include=*.ts 는 no matches 로 죽는다. grep -rn -e 패턴 경로 형태로 쓰거나 따옴표로 감쌀 것. 이 세션에서 두 번 걸렸다.

클라우드 루틴(/schedule)은 Sentry 를 볼 수 없다. .env.local 은 gitignore 대상이고 claude.ai 커넥터 목록에 Sentry 가 없다(Vercel/Gmail/Drive/Calendar 만). 9/1 루틴은 Vercel 데이터만으로 돌았고 /vi/rewards 의 504 1건(edge-middleware 25초 타임아웃, 8/31 12:20Z, 단발성)을 잡아냈다. Sentry 항목을 자동화하려면 claude.ai 에 Sentry 커넥터를 먼저 연결해야 한다.
