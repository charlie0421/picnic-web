3. 값을 치르고 배운 것

설정 파일은 정적 검증을 통째로 빠져나간다

#68 에서 instrumentation.ts 가 서버 config 를 로드하게 고쳤더니, 그 config 안에 잠복해 있던 Sentry.nodeProfilingIntegration() 이 격발됐다. 이 API 는 @sentry/nextjs v9 에 없다(typeof → undefined).

Failed to prepare server TypeError: An error occurred while loading
instrumentation hook: d.nodeProfilingIntegration is not a function

배포됐으면 전 요청 500 이었다. 그런데 tsc·vitest·next build 는 모두 통과한다. 설정 파일은 빌드 시 실행되지 않기 때문이다. 리뷰어가 서버를 직접 띄워서 잡았다.

교훈: 설정 파일을 건드렸으면 next start 로 부팅하고 요청을 보내라. 이 부류를 막으려고 __tests__/sentry-config-contract.test.ts 를 만들었다 — 소스를 구조로 읽어 계약 위반을 잡는다. 수정 전 커밋에 대고 돌려 실패하는 것을 확인한 뒤 통과시켰다.

번들 포함 ≠ 실행 성공

#68 을 검증할 때 빌드 산출물에서 config 고유 문자열(/api/ping)을 찾아 "서버 config 가 번들에 들어갔다"까지 확인하고 완료로 봤다. 그 코드가 실행될 때 어떻게 되는지는 확인하지 않았다. 위 부팅 장애가 그 틈으로 나왔다.

내 수정이 네 라운드 연속 새 결함을 만들었다

#72 의 로그 레벨 작업에서 벌어진 일이다. 매 라운드 리뷰가 결함을 찾았고, 고칠 때마다 새 결함이 나왔다. 원인이 매번 같았다.

라운드내가 한 것왜 틀렸나
1"익명 유발 가능하면 warn"축이 틀렸다. 올바른 축은 "운영자 조치가 필요한가"
2jose 오류 코드로 분기가장 중요한 두 경우가 반대로 동작. audience env 누락(서버 사고)이 ERR_JWT_CLAIM_VALIDATION_FAILED → warn 으로 침묵
3Error 메타데이터 allowlistPostgrestError.details 는 진단 필드가 아니라 위반한 행·값. Key (email)=(secret@example.com) already exists. 가 그대로 전송

공통 원인: 어떤 값이 민감한지, 어떤 오류가 어느 부류인지를 코드에서 추측했다. 3번이 특히 나쁘다 — #73 에 "키 패턴 추측을 버릴 것" 이라고 내가 직접 적어 놓고 같은 실수를 반복했다. 타입 정의는 조사했지만 그 필드에 실제로 무엇이 담기는지는 확인하지 않았다.

결국 ce801bd3(이관 80건)으로 되돌리고 #76 에 기록했다. 정제가 있다는 착각이 정제가 없는 것보다 위험하다고 판단했다.

테스트가 결함을 통과시킨 방식

지난 핸드오프에도 같은 항목이 있었는데 또 나왔다.

  • ExternalMonitoringTarget 테스트 2건은 이름과 "throw 안 함"만 확인해서 본문이 통째로 주석 처리된 빈 스텁으로도 통과했다
  • 신규 테스트 6건이 mock 기반이라 SDK event processor·breadcrumb·RequestData 를 전혀 거치지 않았다. 2,000건 넘는 테스트가 green 인 상태에서 HIGH 결함이 나왔다

후반부터는 구현 전에 RED 를 확인하는 것을 원칙으로 삼았다. 수정 전 커밋에 대고 테스트를 돌려 실패하는 것을 본 뒤 통과시켰다.

4. 반드시 알고 있어야 할 것

Sentry 는 기본 integration 으로 자동 수집한다

Console 과 RequestData 가 SDK 기본 16개에 포함된다. 애플리케이션 코드를 거치지 않는다. console.error 원문이 breadcrumb 가 되고, 헤더·쿠키·쿼리스트링이 자동 수집된다. 로그 타겟 한 곳만 정제해서는 새어 나간다.

beforeSend 는 에러 이벤트 전용이다

// @sentry/core build/cjs/client.js:888-892
if (isErrorEvent(processedEvent) && beforeSend) return beforeSend(...);
if (isTransactionEvent(processedEvent)) { if (beforeSendSpan) ... }

transaction/span 은 beforeSendTransaction/beforeSendSpan, Replay 는 beforeAddRecordingEvent 가 따로 처리한다. 하나라도 빠지면 우회로가 된다.

스키마는 picnic-supabase 소유다

이 레포에 supabase/migrations/*.sql 를 만들지 않는다. #66 에서 scripts/*.sql 11개를 지운 근거는 프로덕션 pg_proc 직접 조회다 — 함수 14개 중 12개 부재, 존재하는 2개도 스키마가 달랐다(auth.is_admin → 실제 public.is_admin).

이 레포는 Vercel Preview 배포가 없다

머지 전 시각 확인이 불가능하다. 검증은 로컬(next start), 시각 확인은 머지 후 Production.

#77 이 가장 중요하다

레포 코드와 PortOne V2(Standard Webhooks)의 서명 스킴이 5가지 모두 다르다 — 헤더 이름, 서명 값 형식, HMAC 키 유도, 서명 대상, 출력 인코딩. 프로덕션 시크릿이 whsec_ 접두어(Standard Webhooks 규격)인데 코드는 그 문자열을 원본 키로 쓴다.

웹훅은 PortOne 결제의 유일한 적립 경로다(verify 는 "pending" 만 반환). PortOne 을 켜는 순간 첫 결제부터 청구 완료 + 적립 0건이 된다. 오픈 체크리스트에 넣을 것.
