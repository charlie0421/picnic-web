포트원 TEST·LIVE 결제수단 통합

2026년 11월 25일 설계 검토안. 별사탕 구매 화면에서 고객이 가맹점 결제창에 표시된 수단을 선택하면 같은 주문으로 결제, 지급, 전액 환불, 회수를 처리한다. TEST와 LIVE는 같은 처리 규칙을 사용한다. 주문, 채널 자격 증명, 알림과 원장은 환경별로 구분한다.

카드, 간편결제, 계좌이체, 가상계좌, 휴대폰 결제, 상품권 등 가맹점이 제공하는 일회성 결제가 대상이다. PG가 통합 선택창을 제공하면 고객은 그 안에서 수단을 고른다. SDK가 호출 전에 결제수단을 요구하면 PICNIC에서 해당 채널의 수단을 먼저 선택하게 한다. 전용 카카오페이 채널과 KG 결제창 안의 카카오페이는 서로 다른 채널로 기록한다. 실제 제휴 여부는 환경별 가맹점 설정으로 결정한다. KG이니시스 연동 · 카카오페이 연동

설계 결정

기존 운영 화면의 카드 요청만 바꾸면 새 주문과 환불 원장에 연결되지 않는다. TEST의 카드 판정을 완화하는 방법도 모바일 복귀, 입금 대기, 운영 대사를 해결하지 못한다. 서버 주문에 결제 경로를 고정하고 결제사별 호출 방식을 분리한다. 주문과 지갑의 기존 지급·환불 절차를 재사용한다.

시점서버의 처리고객 결과
주문 생성환경, 상점, 채널, 선택 가능한 수단, 견적, 설정 버전을 고정한다. 요청 재전송은 기존 주문과 대조한다.브라우저를 새로 열어도 같은 주문을 조회할 수 있다.
인증 후 복귀주문 소유자와 포트원 거래를 확인한다. 수동 승인 채널은 승인 의도를 저장한 뒤 한 번 호출한다. 결과를 잃으면 포트원을 조회한다.앱 전환이나 새로고침이 두 번째 청구로 이어지지 않는다.
가상계좌 발급발급 시점에 유효했던 주문과 입금 기한을 보관한다. 이후 확인한 입금에 발급 당시 조건을 적용한다. 입금 사실이 확인될 때까지 지급을 보류한다.입금 대기와 지급 완료를 구분한다.
결제 완료서명된 웹훅 또는 재조회로 처리를 시작한다. 서버가 해당 환경에서 조회한 결제 상태, 금액, 통화, 주문과 거래 식별자를 검증한다. PG별 응답에서 확인할 수 있는 수단·할인 정보를 검증한다.지갑에 기본·보너스 별사탕을 한 번 지급한다.
전액 환불취소 요청과 환불 성공을 구분한다. 성공한 전액 환불은 원거래에 연결한다. 지급 전이면 이후 지급을 막고, 지급 후이면 기존 환불 원장으로 회수한다. 판매 종료나 채널 교체 후에도 과거 주문을 처리한다.취소 알림이 반복되거나 순서가 바뀌어도 회수는 한 번이다.

구현 순서와 통과 기준

  1. 채널 설정과 주문 계약. picnic-supabase에 추가 마이그레이션을 만든다. create_web_payment_order, prepare_web_payment_provider_context, get_web_payment_provider_binding, authorize_web_payment_provider_entry와 웹 주문 DTO를 확장한다. 기존 주문·PayPal 호환성, 같은 주문 요청의 재전송, 잘못된 채널 및 TEST/LIVE 교차 사용을 시험한다. 브라우저에서 가격이나 자격 증명을 지정할 수 없어야 한다.
  2. 구매 화면과 승인. StarCandyProductsPresenter, usePaymentHandlers에서 주문 기반 결제로 진입한다. lib/payment/portone-test/의 서비스, 전송, 저장소 코드를 재사용해 서버가 검증한 환경과 채널로 SDK 요청을 만든다. 채널마다 지원하는 PC·모바일 호출, 필수 구매자 필드, 수동 승인 가능 여부를 고정한 SDK 선언과 대조한다. 동시 확인과 승인 응답 유실 시험에서 같은 주문의 승인 호출은 최대 한 번이다.
  3. PC·모바일 복귀. PortOneTestCheckout.tsx, portone-test-browser.ts, 포트원 콜백에서 원래 주문으로 돌아간다. 복귀 URL에서 받은 결제 ID만으로 승인하거나 지급하지 않는다. 로그인 만료, 앱 복귀, 중복 콜백, 변조, 저장소 실패 후에도 원래 주문만 조회한다. 승인 토큰을 로그나 영구 브라우저 저장소에 남기지 않는다.
  4. 지급과 입금 대사. 20261117093017의 기존 대사 큐를 확장한다. 서명 알림 접수와 포트원 재조회 결과를 영속화한다. bind_web_payment_provider_identity, receive_web_payment_purchase와 지갑 지급 작업자를 연결한다. 발급만 한 주문의 지급 0건, 유효한 입금의 지급 1건, 기한 경과와 알림 유실 시 복구를 검증한다.
  5. 전액 환불. 20261125072400의 기존 마이그레이션은 보존하고 후속 마이그레이션에서 환불 접수의 주문·원거래 검사를 확장한다. 설정 폐쇄 후 접수, 실패 후 성공한 취소, 장기 대기, 최종 실패를 구분한다. 환경과 원거래에 연결한 취소 키로 중복 접수를 방지한다. 이미 소비한 잔액도 기존 refund_verified_purchase 정책으로 검증한다.
  6. 통합 검증. 환경 × 채널 × 활성 수단 × PC·모바일 조합별로 결제, 지급, 전액 취소, 회수 결과를 기록한다. 별도 DB 연결에서 지갑을 읽어 지급·회수 각 1건을 확인한다. 취소가 지급보다 먼저 확정되면 지급 0건이어야 한다. TEST용과 LIVE용 코드는 합성 거래와 격리 DB에서 검증한다. 실제 거래 증거와 구분해 기록하고 결제 코드·SQL은 구현과 다른 공급자가 검토한다.

구현 중 확인할 계약

각 채널의 활성 수단 목록, 승인 방식, 모바일 반환값, 가상계좌 입금 기한, 취소 완료 응답, 할인 시 주문액과 환불액의 관계를 확인한다. 증거가 없는 조합은 검증 대기로 남긴다. 계좌 환불에 필요한 정보의 취급과 키 교체 후 과거 거래의 조회 방법을 해당 PG 계약에서 확인한다. 실제 채널 활성화, 운영 DB 적용 및 실제 청구는 별도 승인 후 수행한다.
