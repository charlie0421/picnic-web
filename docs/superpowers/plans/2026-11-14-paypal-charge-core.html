PayPal 서버 청구 core 구현 계획 · U1

2026-11-14 · 로컬 구현 범위. 사용자는 확인 질문 없이 계속 진행하도록 요청했다. 조정자는 기존 승인 T5에서 외부 효과를 주입하는 서버 core만 먼저 구현하기로 정했다. 이 문서는 실제 결제·운영 설정·자격증명 조회·DB migration·배포 승인으로 사용하지 않는다.

Goal: 실제 결제 연결 없이 서버 주문의 CREATE/CAPTURE/RECONCILE/STATUS 순서와 거부 경계를 시험한다. Architecture: 기존 current8 RPC repository, 미구현 binding source interface, 기본 closed credential resolver, 명시적 fetch 주입 transport를 조합한다. route/UI/운영 조합을 만들지 않는다. Tech stack: Next.js·TypeScript·기존 Supabase JS·node:crypto·Vitest. 새 의존성은 없다.

Spec: 승인 준비 설계와 T5 로드맵. 작업자는 TDD/writing-good-tests를 읽고 승인한 파일만 편집한다. 시험·SQL·Docker·Node·HTTP·타입검사는 조정자만 실행한다. 네이티브 하위 에이전트는 쓰지 않는다.

1. 원본 대조와 접근 선택

읽기 전용 조사 task_5d37dd8f20dc / ctx_35695b44bb80(실제 Opus5.5/high)는 W 4158c13563959a765e1aeb2d14116cad153d1173와 D e0ba366ba3b02e151b9fb2ab8e3a272af72d2ae5의 검증 사본을 대조했다. 기존 capture route는 소유권·금액 검사 전에 POST하고, popup.closed가 capture를 호출한다. 현재 expectedfail2가 이를 보존한다. 새 core만 구현해 이 legacy 결함이 고쳐졌다고 주장하지 않는다.

접근판정
주입형 서버 core → DB binding/HTTP bridge → route/legacy 폐쇄 → SDK UI조정자 선택. 외부 전송 없이 순서와 권한을 먼저 검증하며 각 후속 단위의 미완료 상태를 드러낸다.
legacy capture에 GET만 추가서버 주문·견적·durable intent가 없어 승인 설계에 부족하다. 선택하지 않는다.
route/UI/DB/credential을 한 번에 변경누락 DB 계약과 배포 영향이 섞인다. 이번 단위에서 선택하지 않는다.

2. 전역 제약과 실제 누락 계약

  • 청구 actor는 이후 route의 auth.getUser에서만 온다. U1 함수 입력의 actor/order는 내부 서버 입력이며 브라우저 신뢰 근거가 아니다. UUID·상태·provider/env·금액·통화·quote hash를 검증한다.
  • DB8과 getter25key를 고정한다. service_role 표 SELECT를 추가하지 않는다. 기존 legacy route/UI/PortOne403/types/package/lockfile은 수정하지 않는다.
  • 청구 전 binding credential_ref/version/hash/client_id 및 billing_country를 반환하는 RPC는 없다. U1은 ChargeBindingSource interface만 정의하고 존재하지 않는 RPC를 호출하거나 production binding 구현을 만들지 않는다. 별도 U0에서 owner-first/service-only 조회 계약을 설계·검증한다.
  • PayPal payee.merchant_id는 독립 대조한다. scope.account_id에 대응하는 별도 응답 값은 확인하지 못했다. evidence의 account_id는 고정 context 복사이며 독립 계정 검증이라고 부르지 않는다. 운영 의미 확정 전 개방하지 않는다.
  • intent 뒤 미송신·미완료 종결 상태는 없다. SUBMISSION_UNKNOWN 이후 새 POST·새 주문 권유를 하지 않는다. T6 종결 계약이 별도로 필요하다.
  • 실제 provider·OAuth·운영 DB·설정·스위치·credential·배포를 사용하지 않는다. transport factory는 fetch 인수를 반드시 받으며 import만으로 client를 만들거나 외부 요청을 시작하지 않는다. 기본 resolver는 null이다.
  • 공유 log-event-codes에는 새 사건 코드만 추가한다. 이 파일이 고정됐던 과거 HTTP receipt는 당시 hash의 증거로 유지한다. 과거 실행기의 pin을 수정하거나 새 current source 실행으로 소급하지 않는다. U2는 새 source closure를 사용한다.

ChargeContext는 원본 getter25key의 명시 camelCase projection이다. charge_authority는 반드시 false, quantity는 문자열1, 금액·rowVersion은 문자열이며 quote_expires_at 원문을 보존한다. 원본 settlement_state 등 enum과 예외는 DB SQL에서 정확히 복사한다. 미등록 reason/형식은 RESPONSE이며 숫자로 온 rowVersion을 임의 복원하지 않는다. p_expected_version/p_fencing_version은 문자열로 보낸다. PostgREST bigint 직렬화는 U2 실제 HTTP에서 확인한다.

Outcome kind: STATUS(paymentState/settlementState/reviewRequired), PROVIDER_ORDER_READY(그때만 providerOrderId/replayed), NOT_APPROVED, ORDER_VOIDED, IN_PROGRESS, CAPTURE_PENDING, CAPTURE_FAILED, INTAKE_PENDING(replayed), SUBMISSION_UNKNOWN, NO_PROVIDER_ORDER, REVIEW_REQUIRED, BLOCKED(reason), NOT_FOUND, UNAVAILABLE(stage). stage는 CONTEXT/PREPARE/BINDING/CREDENTIAL/TOKEN/CREATE/LOOKUP/CLAIM/INTENT/SUBMIT/OBSERVE/INTAKE다. browser에는 kind를 state로만 projection하고 newOrderAllowed=false를 유지한다.

시험 checkpoint 뒤 조정자 결정: protocol의 discriminator는 kind:OK/MISMATCH와 reason으로 고정한다. repository는 최상위 camelCase와 native scope의 account_id/merchant_id를 명시적으로 보존한다. STATUS는 owner getter만 호출하고 알려진 원본 paymentState/settlementState/reviewRequired를 kind:STATUS로 반환한다. GRANTED를 PAID/CREDITED로 다시 추론하지 않는다. browser의 추가3필드는 STATUS에서만 허용하며 newOrderAllowed=false다. optional caller signal은 각 operation의 고정 timeout과 함께 적용해 취소와 유한 기한을 모두 보존한다.

사건 코드는 payment.paypal.charge.context.failed, payment.paypal.charge.credential.unavailable, payment.paypal.charge.create.failed, payment.paypal.charge.lookup.failed, payment.paypal.charge.claim.blocked, payment.paypal.charge.intent.failed, payment.paypal.charge.submit.unknown, payment.paypal.charge.observe.review, payment.paypal.charge.intake.failed의9개다. 기존 코드는 바꾸지 않는다.

실연결 전 추가 관문: prepare의 기존 context 재조회는 현재 설정을 다시 승인하지 않는다. U1의 READY는 기존 identity 조회 결과이며 새 결제창 진입이나 외부 청구 권한이 아니다. U0/U3에서 현재 환경·OPEN/new-orders·회전·만료에 따른 provider-order 진입/CREATE 관문을 검증해야 한다. frozen binding 조회만으로 이 live 관문을 충족했다고 주장하지 않는다. 이번 core에는 production 조합이 없다.

4. 평가·전달·관측의 정확한 조건

  • purchase_units는 정확1개, intent=CAPTURE, ORDER id는 기대 link와 일치하고 custom_id는 v2:<server order UUID>다. amount USD와 minor 값, payee.merchant_id를 비교한다. captures는0..1개, capture id는 공식식에 맞고 amount/currency 및 있으면 custom_id도 일치해야 한다. 정상 승인 경로는 여러 capture를 거부한다. REVIEW 경로는 실제 후보를 최대32개까지 별도로 보존하며 이는 공식 schema 상한이 아닌 로컬 작업량 상한이다. 33개 이상은 부분 기록·추가 GET 없이 닫는다. 알 수 없는 상태는 원문을 보존한다.
  • ORDER known6=CREATED/SAVED/APPROVED/VOIDED/COMPLETED/PAYER_ACTION_REQUIRED, CAPTURE known6=COMPLETED/DECLINED/PARTIALLY_REFUNDED/PENDING/REFUNDED/FAILED. 대소문자·공백을 정규화하지 않는다. schema 또는 DB bounded 식 밖의 값은 기록 전에 UNAVAILABLE로 닫는다.
  • 결제자 국가는 공식 schema의 payment_source.paypal.address.country_code와 deprecated payer.address.country_code만 사용한다. 둘 다 있으면 둘 다 기대값과 같아야 한다. shipping·브라우저 언어에서 추정하지 않는다. 있으면 billingCountry와 비교하며 없으면 확인됐다고 부르지 않는다. 국가·shape 등 DB17key로 REVIEW 사유를 표현하지 못하는 경우는 local REVIEW로 닫고 새 청구 POST를 허용하지 않는다. 이미 송신한 POST 뒤에는 제한된 관측 전용 GET이 가능하지만 receive는 금지한다. 이를 sticky DB REVIEW라고 주장하지 않는다. 공급자 status를 가짜 COUNTRY_MISMATCH로 바꾸거나 실제 정상 scope/금액을 고의로 틀리게 기록하지 않는다. 이 제한은 U0/U2 후속 계약에서 별도로 평가한다.
  • 실제 관측된 amount/currency/merchant/custom_id만 evidence에 넣는다. context account_id·actor/order/hash는 내부 귀속값이며 독립 provider 증거와 구분한다. key=KIND:externalId:rawStatus, payload_hash=자신을 제외한 bounded evidence canonical JSON SHA256. 상태가 바뀌면 key가 달라진다. raw PII/update_time/임의 link/provider_completed_at은 넣지 않는다.
  • LIVE host=https://api-m.paypal.com, SANDBOX=https://api-m.sandbox.paypal.com. 다른 runtime environment는 fetch 전에 거부한다. providerOrderId는 ^[A-Z0-9]{1,36}$, requestKey는 UUID다. redirect:error/cache:no-store, mutation retry0. 응답 links를 따라가지 않는다.
  • create/capture에 PayPal-Request-Id와 Prefer:return=representation을 넣는다. create body는 CAPTURE 및 한 purchase unit의 custom_id/amount뿐이며 payee/return_url/cancel_url/application_context는 넣지 않는다. capture body는 {}다. token POST는 client_credentials, 비밀은 에러·로그에 넣지 않는다.
  • 응답은256KiB 누적 bytes에서 중단한다. Content-Length나 전체 text를 먼저 읽은 뒤 길이만 재는 방식으로 상한을 주장하지 않는다. malformed/oversized JSON은 body:null이다. token10s/create15s/get10s/capture20s는 조정자 기술값이며 실제 provider SLA가 아니다. 숫자 변환은 금액에 쓰지 않고 ASCII 양수 minor/정확2자리 decimal을 문자열로 처리한다.
  • resolver 반환 clientId는 고정 expectedPayPalClientId와 대조한다. bindingVersion/hash는 선택 키이며 반환에 없는 hash를 검증한 척하지 않는다. 잘못된 binding shape·env/context/order/prepare scope는 token 전에 거부한다. 서명·credential 원본 검증은 실제 resolver 구현과 별도 관문이다.

DB/web 시계 차이는 margin으로 줄일 뿐 제거하지 못한다. 원문 timestamp 문자열과 µs를 보존하고 local 기한 비교를 DB 시계 권위로 부르지 않는다.
