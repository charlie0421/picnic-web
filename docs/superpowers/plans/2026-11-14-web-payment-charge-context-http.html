T5 소유자 getter PostgREST HTTP 검증 계획

2026-11-14 · 승인9파일 구현·보완 검증·원 리뷰 계열 재검증 통과. 기존 제품·DB migration·완료된 주문 HTTP 실행기는 동결했다. PG15/17의 실제 getter GET/POST를 검증했고 최초 독립 리뷰 Medium 2건의 보완본을 재실행했다. 원17건은 fixed14/accepted-limit3으로 정산됐다. 재검증의 새 Low R1은 조정자가 권고된 한 줄과 반례를 추가해69개 시험·양PG HTTP로 확인했다. 이 마지막 한 줄은 추가 독립 리뷰를 거치지 않았다. 아래 본문은 승인된 계획이며 현재 실행 결과는 검증 보고서를 따른다. 청구 어댑터·공급자·운영 개방은 미완료다.

작업자: 사용자가 지정한 Orca 오케스트레이션을 유지한다. 작성자는 승인된 파일 편집과 정적 확인만 맡는다. 조정자만 셸 시험·Docker·SQL·HTTP를 실행한다. 구현과 반대 공급자의 고위험 Frontier 리뷰·원 리뷰 계열의 1회 재검증을 유지한다. 네이티브 하위 에이전트를 사용하지 않는다. 각 실행 전에 계정·사용량·모델·권한을 새로 검증한다.

목표: get_web_payment_charge_context(uuid,uuid)의 service-only 권한, owner-first 응답, 고정 견적·정밀도와 읽기 전용 동작을 실제 PostgREST GET/POST로 확인한다.

구조: 기존 factory와 source 검증 helper를 고정 hash의 bytes loader로 재사용한다. 전용 runner·guard·entry를 추가하고 원본 current8 DB에 실제 HTTP를 보낸다. 두 phase의 native snapshot과 상태 digest를 HTTP 결과와 대조한다.

기술: 기존 Python·Node24·esbuild·Supabase JS/PostgREST JS2.112.3, PostgREST14.8, PostgreSQL15.8/17.6. 새 의존성을 설치하거나 버전을 올리지 않는다.

승인 설계: 웹결제 준비 설계, T5 계획, 완료된 DB gate·getter 계약의 HTTP 검증 후속이다.

1. 현재 source와 접근 선택

4. loader·pin·격리 계약

신규 runner는 python3 -I -B로 실행한다. 기존 pair_fixture·setup_db·run을 각각 검증한 source bytes로 compile/exec하고, __file__은 실제 원본 경로·__cached__=None으로 둔다. 예상 module이 sys.modules에 이미 있으면 거부한다. 로드 순서는 pair_fixture→setup_db→order_http_run이다. 정상 import가 이전 pyc나 미검증 module을 선택하지 않도록 loader identity·import 순서를 검사한다. DB helper는 기존 verified_helpers를 새 D manifest와 함께 사용한다.

기존 run.py에서는 LocalDocker·공개 JWT 생성·interpreter evidence 같은 재사용 함수만 쓴다. main()은 호출하지 않는다. 기존 setup_db.verify_source/setup의 과거 HEAD/7migration pin도 우회 호출하지 않고 전용 runner가 현재 계약을 검증한다. W 로컬 기존 실행기의 pyc nit을 고친 것으로 표시하지 않는다. -B는 쓰기만 막는다. 두 디렉터리의 캐시 상태·변화를 기록하고 기존 캐시를 삭제하지 않는다. 새 bytes loader가 일치하는 오래된 pyc와 sys.modules로 우회되지 않는지는 별도 단위시험으로 확인한다. stdlib와 전체 dependency tree의 무결성까지 보장하지 않는다.

W pin 선택: 명시 --web-head의 full40자와 조정자가 고정한 W manifest를 함께 확인한다. manifest 자체의 경로/hash와 허용 경로 집합을 전후 기록한다. 경로 집합은 manifest에 포함할 source 목록이며 HEAD와 달라도 되는 임의 경로 목록이 아니다. 절대경로·상위 경로 이동·중복·symlink·누락/추가 source를 거부한다. 현재 HEAD는 명시값과 같아야 한다. 새로운 커밋 뒤에는 조정자가 새 HEAD를 명시한 manifest를 별도로 준비한다. 자동 HEAD 채택은 없다.

  • frozen: 기존10파일·제품/시험7파일·types는 tracked 상태와 HEAD blob을 확인한다. git status/diff가 깨끗하고 HEAD/manifest/실제 파일 hash가 모두 같아야 한다. 선택된 설치 JS4파일은 Git 대신 manifest와 실제 hash를 대조한다.
  • owned: 신규9파일은 첫 검증·리뷰 동안 untracked 또는 수정 상태일 수 있다. 각 파일은 조정자가 검토해 승인한 manifest hash와 정확히 같아야 한다. tracked/untracked 상태와 diff 유무를 receipt에 기록한다. manifest를 실행 중 자동 갱신하지 않는다.
  • 문서·기존 임시 파일: 이 계획·로드맵·보고서와 기존 task/artifact 디렉터리는 위 source pin 대상이 아니다. 이들의 존재를 이유로 전체 작업트리 clean을 요구하지 않는다. 소유9파일과 frozen 목록만 경로별로 판정하고 다른 변경을 함께 커밋하지 않는다.
  • 최종 커밋: 검증·독립 리뷰 후 신규9파일과 관련 문서를 커밋한다. 실행한9파일·frozen source와 최종 Git blob의 hash가 같은지 대조해 실행 증거를 커밋에 연결한다. HEAD만 바뀌고 검증 source/의존성/config가 같으면 HTTP를 반복하지 않는다. 실제 실행 HEAD와 최종 커밋을 모두 기록하고 최종 HEAD에서 재실행했다고 주장하지 않는다. 검증 source·의존성·실행 config가 바뀌면 영향받는 검증을 새 label로 실행한다.

D는 e0ba366ba3b02e151b9fb2ab8e3a272af72d2ae5와93파일 후보 manifest·48개 의존성 SQL hash를 확인한다. 설치 source4파일의 package 버전은2.112.3이며 esbuild 버전도 기록한다. 전체 node_modules hash는 미고정 한계다.

한 실행에 PG/PostgREST/Node의3개 컨테이너와 단일 internal network만 만든다. PG15/17 변형을 포함한 고정4종 이미지 중 해당3개를 --pull never로 사용한다. host port0·readonly rootfs·tmpfs/자원 한도·Node2개 readonly bind를 기존 factory로 검증한다. 정확 CID/image/run UUID/phase/member를 삭제 직전 재검증하고 개별 absence가 모두 True일 때만 완료다. unknown·foreign·inspect 실패에서 이름/label 추측 삭제·자동 재시도는 하지 않는다. 원래 작업 오류와 cleanup 오류를 함께 보존한다.

5. DB 설치와 두 phase

원본 BOOTSTRAP → 선택된48개 dependency SQL → positive app/debit/refund control
→ 원본8개 migration(postgres nosuperuser/nobypassrls)
→ synthetic authenticator → seed → privileged fixture → baseline A
→ PostgREST 시작 → HTTP A → observer A
→ stop commit → baseline B → HTTP B → observer B
→ source/artifact hash 확인 → 정확 CID3개/network 정리·개별 absence

positive control은 원본 positive-refund-control-complete로 끝나야 한다. current8 bridge와 달리 이 실행기에서는 아직 설치를 실측하지 않았다. dblink/HBA 변경·upgrade fixture는 필요하지 않다. schema cache는 모든 DDL을 끝내고 PostgREST를 시작해 적재한다. 시작 뒤 seed용 함수·DDL을 추가하지 않는다. native envelope에 temp test utility가 필요하면 첫 HTTP 전에 준비한다.

역할·권한 오류가 나면 원문을 fixture/설치 실패로 남기며 해당 case의 제품 결함이나 통과로 집계하지 않는다. seed를 자동으로 fixture_admin으로 올리거나 ACL을 늘려 통과시키지 않는다. 역할 경계 변경이 필요하면 별도 checkpoint로 제안한다. 각 SQL 접속 user와 역할 전환 증거를 receipt/log에 보존한다.

seed 교정: 원본 settings 초기 행은 PAYPAL LIVE와 PORTONE LIVE뿐이다. SANDBOX/TEST를 UPDATE만 하면 새 환경은 생기지 않는다. seed는 PAYPAL SANDBOX/USD·PORTONE TEST/KRW를 명시 INSERT하고 현재 환경의 unique 제약을 지키며 LIVE의 current 표시를 먼저 해제한다. 모든 주문·context·binding은 OPEN인 합성 설정에서 만든다. 회전용 두 번째 binding도 미리 생성한다. 이 설정은 disposable fixture 안에서만 사용한다.

준비 완료는 service JWT의 raw POST getter가 임의 UUID2개에 HTTP200·정확3key NOT_FOUND를 반환할 때만 인정한다. 함수 부재404·schema-cache 오류·503은 준비 완료가 아니다. 각 probe1초와 유한 전체 deadline을 두며 raw fetch 자체는 재시도하지 않는다. 준비 polling과 실제 시험의 호출 수를 분리한다.

config 교정: config.json은 두 phase의 marker·case UUID·공개 JWT·소유 주소를 담아 한 번만 만든다. phase는 Node argv A/B로 선택한다. bundle/guard/config를 phase 사이에 덮어쓰지 않는다. 각 phase의 고유 완료 marker와 Node exit를 검사하고 전후3개 artifact hash를 비교한다.

digest 교정: settings/profile이 의도적으로 바뀌므로 A와 B의 전체 digest가 같다고 요구하지 않는다. baseline A↔A 후, baseline B↔B 후를 각각 비교한다. stop 전후에는 허용한 settings 필드와 actor C의 deleted_at만 달라졌는지 확인한다. 금융/FULL은 모든 관측에서0이다. 이를 위해 원 제안의3회 대신 seed 후·A 후·stop 후·B 후의 네 native 관측을 사용한다.

  • timestamptz의 timezone 표현과 원문 µs를 측정한다. 형식 차이가 나면 session/표현 전제를 조사하고 무분별한 문자열 정규화로 정밀도 손실을 숨기지 않는다.

7. wire·guard·observer 증거

호출마다 proxy tap1개를 요구한다. method·정확 path/query·GET 빈 body·POST 두 key와 null·header·upstream path·raw status/content-type/cache-control/body를 기록한다. apikey와 Authorization은 해당 공개 JWT와 정확히 같고 Cookie·브라우저 토큰·X-Retry-Count가 없어야 한다. GET의 Accept-Profile, POST의 Content-Profile/JSON Content-Type을 검사한다. raw cache-control은 관측값이며 향후 웹 route의 private/no-store·503 계약으로 부풀리지 않는다.

guard와 proxy는 정확 getter path·GET/POST만 전달한다. GET query는 p_actor_user_id/p_order_id의 부분집합이며 중복 없이 UUID 또는 측정용 "null"만 허용한다. select/order/미지 key·중복 key·다른 RPC/table·path 변형·다른 method·query 있는 POST를 거부한다. 기존 literal lookup·Resolver prototype·child export7개·Worker 등 명시 거부도 재사용한다. 실제 실행 항목 목록과 개수를 기록하며 과거15+38 개수를 코드 없이 자동 승계하지 않는다.

협조형 wrapper의 method/path/query와 raw socket의 주소 경계를 구분한다. ChildProcess.prototype.spawn·native process.binding 등 전체 primitive를 중재하지 않는다. 외부망 경계는 Docker internal network이며 hostile-code sandbox를 주장하지 않는다.

observer는 실제 getter owner/SD/STABLE/search_path/ACL, private helper/command의 외부6역할 EXECUTE 없음, service_role 표 SELECT 없음, catalog/PROVIDER_WORKER·최종 manifest assert·차용 CREATE 회수를 확인한다. 표 경로는 HTTP guard에서 열지 않으며 표 SELECT의 실제 HTTP 거부를 검증했다고 말하지 않는다.

상태 digest는 orders/quotes/contexts/links/observations/attempts/profiles/settings/bindings/intakes를 포함한다. 금융/이력31개와 verification_results/full proofs/settlements/settlement leases의 실제 존재·0행을 검사한다. getter 호출 자체가 설정·주문·원장 어느 것도 바꾸지 않아야 한다. 경쟁·잠금 중 getter 무대기는 앞선 D native 증거로만 인용한다.
