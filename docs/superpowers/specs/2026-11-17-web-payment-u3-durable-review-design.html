사용자는 C 정책 방향을 선택했다. 구체 설계는 아직 승인되지 않았다. 원 후보의 FAIL 이력과 조정자 보완을 함께 보존한다. 최종 G9 한정 재확인은 5건 FIXED·builder PASS이며 실행 검증이나 사용자 설계 승인이 아니다. 범위·한계는 최종 검토 상태 절을 따른다. 제품 구현·DDL 적용·운영 조회·해제·배포·credential 개방은 실행하지 않았다.

청구 결과 분류가 DB에 확정되기 전에 장애가 나면 정상 결제도 자동 접수를 보류한다. 송신자 권한을 intent 시점 신원에 묶고, 청구 후 GET 전에 read cycle을 DB에 연다. 접수와 지급 명령은 같은 보류 상태를 읽는다.

이 보완은 원 Sol 수정 재검증의 F-H1..3, F-M1..4, F-L1에 대한 조정자 작성안이다. 원 14건의 FIXED9/PARTIAL5와 builder FAIL은 역사 기록으로 보존한다. 아래 보완을 검토하기 전에는 잔여가 해소됐다고 정산하지 않는다. C 방향은 확정됐으나 구체 설계·구현·DDL·운영 실행은 미승인이다.

G0. 우선순위와 범위

  • G1–G8이 v2 원문 10부의 지정 조항을 대체한다. 지정하지 않은 송신자 tuple, C hold, 접수·하류 비종결 차단, 불변 사실, 감사 해제, OG1–OG6, S0/S1 공개 잔여는 유지한다. 이 보완은 프로그램 본문이나 실행 계획이 아니다.
  • root의 기술 선택이다. 실제 DB/HTTP/Edge 실행·SQL commit·crash 실험·최대 시간 실측을 하지 않았다. 검토 대상은 root가 추가·대체한 계약과 그 소비 경로다. 원 Opus 문서 전체의 재투표를 요청하지 않는다.

G1. 호환 claim 경계와 cutover 필수 조건 — F-H1

  • v2 6부의 “같은 배포 묶음 권고”와 budget key 누락 시 raw count 대체를 철회한다. PayPal V2 검증은 DB에서 consumer contract 2를 구분한다. 기존 claim_web_payment_purchase(uuid,uuid,integer)는 PayPal V2에 항상 NOT_CLAIMABLE을 반환하고 attempt·lease를 쓰지 않는다. PortOne의 기존 경로는 유지한다.
  • 신규 public.claim_web_payment_purchase_v2(p_inbox_id uuid,p_worker_id uuid,p_lease_seconds integer) returns jsonb. lease_seconds 범위 1..300. owner wallet_command_owner, SECURITY DEFINER, search_path='', 첫 READ COMMITTED 검사, service_role만 EXECUTE, PUBLIC/runtime revoke와 catalog/manifest PROVIDER_WORKER 등록 규칙은 v2와 같다. 이것이 서비스 RPC S8이며 “서비스 7개”를 8개로 대체한다.
  • 응답 contract_version='web-purchase-verification-claim.v2'. NOT_CLAIMABLE 정확 key는 {contract_version,outcome,grant_eligible:false}. CLAIMED 정확 key는 {contract_version,consumer_contract:2,outcome,inbox_id,lease_token,inbox_row_version,lease_until,attempt_count,budget_attempt_count,payload,coverage:'SCOPE_ONLY',grant_eligible:false}. UUID/bigint/number 규칙은 v2와 같다. 새 worker는 이 응답의 contract와 budget_attempt_count를 필수로 검사하며 fallback하지 않는다. 구 DB의 함수 부재·잘못된 응답은 닫힌 실패다.
  • 새 D web-purchase-worker는 WEB_PURCHASE_V2에 v2 claim만 호출한다. 기존 함수의 내부 로직은 private claim core로 공유할 수 있다. 이는 신뢰된 service 소비자의 호환 API 선택이며 바이너리 원격 attestation이라고 주장하지 않는다.
  • 새 T10 web_payment_verification_claim_contracts: insert-only, id uuid PK, inbox_id FK, claimed_inbox_version bigint, lease_token_hash sha256, consumer_contract CHECK=2, worker_id uuid, recorded_at; UNIQUE(inbox_id,claimed_inbox_version). owner/RLS/runtime 표 권한 0/immutable guard/HISTORY_LEDGER inventory는 증거 표 공통 규칙과 같다. v2 claim의 inbox 갱신과 T10 삽입은 한 트랜잭션이다. raw lease token은 새 표에 복사하지 않는다.
  • prepare_web_purchase_verification_result는 현재 PayPal V2 lease에 대해 wallet→order→inbox 잠금 뒤 T10의 inbox/version/token hash 일치를 검사한다. 누락·불일치면 P0001 WEB_PAYMENT_VERIFICATION_CONSUMER_UNSUPPORTED, 새 결과·terminal REVIEW·예산 변경 0이다. 이 검사는 caller REVIEW를 정규화하거나 signer challenge를 만들기 전이다. attest의 prepare 재호출도 같은 검사를 통과해야 한다. 기존 terminal 결과 replay는 기존 행만 반환한다.
  • 따라서 새 DB 아래의 구 worker는 새 PayPal lease를 얻지 못한다. migration 전 구 lease로 보낸 늦은 prepare/attest는 새 T10 근거가 없어 거부된다. 실제 provider 근거 REVIEW를 RETRY로 바꾸지 않는다. 새 worker의 hold 예산 분리와 원 REVIEW 불변은 유지한다.
  • 필수 cutover 선행조건: 기존 함수 본문으로 이미 실행 중인 트랜잭션이 migration 뒤 계속되는 창은 API 버전만으로 소급 차단할 수 없다. OG2의 배포 승인 후 WEB_PURCHASE_V2 검증·정산 신규 실행을 중지하고 구 worker·in-flight DB 명령을 drain/fence한다. 관련 기존 트랜잭션이 모두 끝났다는 증거를 확보하기 전에는 migration·재개를 허용하지 않는다. 실행 종료를 검증할 수 없으면 cutover는 차단이다. 새 API·T10 guard 적용을 확인한 뒤 호환 worker만 재개한다. 이번 작업은 이 운영 절차를 실행하지 않는다.
  • 증거 의무: 구 binary→구 claim은 NOT_CLAIMABLE/행0, 구 lease→늦은 prepare/attest는 정확 P0001/결과0, 새 v2 worker의 hold 경쟁 9회 뒤 terminal REVIEW0·감사 release 후 재후보, 비PayPal 경로 보존, cutover drain 부재 시 재개 금지를 각각 검증한다.

G2. 기존 attestation owner의 isolation 검사 — F-H2

  • v2 4부·8부의 helper 호출 공통 규칙에 예외를 둔다. wallet_attestation_owner 소유의 attest_web_purchase_verification_result, attest_web_purchase_grant, attest_verified_web_purchase 첫 문장에는 current_setting('transaction_isolation') 검사와 동일 P0001 WEB_PAYMENT_ISOLATION_UNSUPPORTED 거부를 직접 둔다. 이 세 함수는 assert_web_payment_read_committed를 호출하지 않는다.
  • private isolation helper는 command owner의 나머지 함수에서 사용한다. wallet_attestation_owner, runtime role, PUBLIC에 그 helper EXECUTE를 추가하지 않는다. 기존 role membership·owner도 변경하지 않는다. 기존 prepare/apply 호출의 명시 EXECUTE는 유지한다.
  • PUBLIC ACL 검증은 acl grantee=0 부재로 한다. has_function_privilege에는 실제 runtime role만 전달한다. pseudo-role PUBLIC을 role 이름으로 조회하지 않는다.
  • 증거 의무: service→각 definer owner의 정상 READ COMMITTED/MAC/lease 양성과 RR·SERIALIZABLE의 정확 P0001 음성을 분리한다. 42501이나 membership 확장은 성공 근거가 아니다. PayPal·PortOne 세 attestation 진입을 보존한다.

G3. partial VOIDED와 의미 판정 순서 — F-H3

  • v2의 RESPONSE_ORDER_VOIDED 입력은 2xx PARSED, requested ADVERSE이며 다음 둘 중 하나다. 표현 가능한 실제 ORDER VOIDED fact가 있거나, ORDER fact를 만들 수 없어 정확 caller assertion UNRECORDABLE_PROVIDER_FACT{fact_kind:'ORDER',reason:'ADVERSE_STATUS_PARTIAL'}가 있다. 가짜 id·merchant·scope·status를 채우지 않는다. 보호 GET의 READ_ORDER_VOIDED도 같은 대안이다.
  • merchant/id 등 필수값 누락의 partial VOIDED는 ADVERSE category와 assertion을 정상 commit한다. 단순 input 오류나 ABSENT/ABANDONED로 대체하지 않는다. 실제 fact가 있으면 native adverse가, 없으면 신뢰된 W의 SERVER_REPORTED assertion이 sticky 원천이다.
  • shape/키/상한/권한의 형식 검증은 유지한다. 그러나 유효 evidence에 실제 VOIDED·UNRECOGNIZED·native REVIEW가 있는데 requested CLEAN/NO_CAPTURE의 nominal 조건과 다르다는 이유만으로 관측 전에 거부하지 않는다. 사실의 native 결과와 DB 파생 adverse를 먼저 산출하여 effective ADVERSE/CLASSIFICATION_INCONSISTENT로 낮춘다. target category의 긍정 상태 조건은 CLEAN 허용 조건이지 adverse evidence 폐기 조건이 아니다. 형식이 잘못된 요청 전체에 대한 22023 계약까지 완화하는 것은 아니다.
  • 증거 의무: POST·GET 각각 merchant 누락/id 누락 partial VOIDED, 완전 VOIDED+capture0/1, 유효 VOIDED fact를 포함한 위조 CLEAN/NO_CAPTURE를 확인한다. ADVERSE assertion/fact가 commit된 뒤 정상 GET·absence release로 풀리지 않아야 한다.

G4. batch observation key 순서와 queue 잠금 — F-M1

  • P1·P2 complete·late는 native observation helper를 첫 호출하기 전에 전체 facts의 observation advisory lock 집합을 계산한다. native와 동일한 prefix 'web-payment-observation.v1', provider/environment/source/key의 jsonb 배열 정규 text→SHA256 앞 64bit signed bigint 변환을 사용한다.
  • 서로 다른 실제 lock bigint를 오름차순으로 선취득한다. hash 충돌은 같은 lock으로 dedupe한다. 그 뒤 사실은 원 입력 순서로 처리한다. fact_results/index/receive_fact_index/bind flag는 재정렬하거나 없애지 않는다. 같은 트랜잭션이 native helper의 같은 key lock을 재획득하는 것은 허용한다.
  • 전역 순서: 자신의 wallet→order→필요 attempt/inbox/lease→정렬된 observation key 전체→단일 bind의 unique-link 대기→필요 source lock→기존 T7 UPDATE. batch의 bind=true는 최대 1개, CAPTURE에만 허용한다. 단건 기존 API는 한 key만 사용하며 다른 wallet/order를 잡지 않는다. unique-link 삽입은 native의 단회 bind/on-conflict 규칙을 유지한다. 관련 경로에서 이보다 이른 다른 key 선취득을 허용하지 않는다.
  • queue_refresh_one과 P1/complete/release의 queue 이벤트 갱신은 이미 존재하는 T7만 UPDATE한다. INSERT/upsert를 하지 않는다. enroll만 T7을 INSERT ON CONFLICT DO NOTHING한다. claim/finish/주기 refresh는 T7만 잠그고 그 뒤 wallet/order 잠금을 취득하지 않는다. hold plain read는 queue 권한이 아니며 cycle open·receive가 자신의 잠금과 최신 판정을 다시 검사한다.
  • 증거 의무: 다른 사용자·주문에서 X/Y와 Y/X의 반대 순서, P1/complete/late/기존 단건 혼합과 unique-link 경쟁을 두 연결로 검증한다. enroll의 FK 대기와 order holder의 기존행 UPDATE 전용 조건도 시험한다. “모든 deadlock 불가능”이라는 runtime 주장은 하지 않는다.

G5. executor deadline과 commit 불명 — F-M2

  • v2 7부의 hardDeadline55와 25초 reserve를 철회한다. STARTED 기록 응답을 받은 시점을 t0로 한다. 새 queue claim 시작 cutoff는 t0+20초다. providerReadDeadline은 t0+55초이며 provider/resolver 읽기의 종료·새 시작 cutoff다. invocation 전체가 55초 안에 끝난다는 보장이 아니다.
  • owner/getter·binding 등의 읽기는 남은 읽기 budget과 각 10초 상한 중 작은 timeout을 쓴다. replay prepare 등 이미 시작한 DB 명령과 모든 write는 해당 RPC의 10초 client timeout까지 응답/오류 정산을 await한다. Promise.race로 write를 버리지 않는다. DB commit 완료를 client timeout으로 단정하지 않는다.
  • 새 open은 providerReadDeadline까지 최소 20초가 남았을 때만 시작한다(최대 open 응답 대기10초+GET 읽기10초). open 응답 뒤 실제 경과시간으로 남은 GET budget을 다시 계산한다. GET timeout은 min(10초,남은 provider budget)이다. 양수일 때만 시작한다.
  • OPENED 뒤 남은 GET budget이 없거나 run signal이 GET 시작 전에 취소됐으면 GET을 보내지 않고 complete NO_DATA/READ_LOCAL_BUDGET_EXHAUSTED 또는 READ_LOCAL_CANCELLED를 기록한다. http/body/observed IDs는 null, 사실·assertion은 0이다. 이는 GET을 시작하지 않았다는 로컬 판단이며 capture POST 미송신 증거가 아니다. GET을 시작했다가 취소되면 실제 transport 분류를 쓴다. 이미 획득한 parsed adverse 판단을 NO_DATA로 지우지 않는다.
  • open 뒤에는 GET 시도 또는 위의 명시적 미시작 completion 중 하나를 정산한다. complete→finish→FINISHED 기록은 provider read cutoff 이후에도 각각 await한다. 각 client timeout10초를 두며 쓰기 불명은 별도로 집계한다. 10초 STARTED+55초 읽기 구간+complete/finish/FINISHED 각10초의 정적 여유를 고려해 route maxDuration과 호출 timeout의 운영 최소 제안은 120초다. 실제 플랫폼 종료 보장은 OG2 확인 전 미검증이다.
  • complete 응답 불명은 두 경우다. DB commit 전 실패면 OPEN이 남아 sweep 시 ABANDONED가 된다. commit 후 응답 유실이면 저장 CLEAN/ADVERSE/NO_DATA가 남고 sweep하지 않는다. 이후 DB 상태를 조회하기 전에는 어느 쪽인지 추정하지 않는다.
  • finish STALE_LEASE는 성공 정산이 아니다. queue를 덮지 않고 metrics.stale_lease를 증가시키며 run result PARTIAL_STALE_LEASE로 기록한다. complete가 확인된 결과 수와 finish 소유권 실패 수를 각각 보존한다. FINISHED 기록 실패는 route503이며 STARTED-only health가 드러낸다. 신규 metrics key stale_lease와 result enum PARTIAL_STALE_LEASE를 S7 ABI에 추가한다.
  • 증거 의무: 느린 owner/prepare/binding, open10초, 남은20초 경계, open 뒤 budget 소진·취소, GET 취소 후 NO_DATA, complete 전/후 commit 응답 유실, finish10초·STALE_LEASE·FINISHED 실패를 clock-controlled 검증한다. 항목당 GET≤1, charge claim/intent/CREATE/capture POST0은 유지한다.

G6. overflow 없는 retry/backoff — F-M3

  • 검증 budget_attempt_count는 max(0,raw attempt_count−기록된 INTAKE_HOLD_PENDING RETRY 수)다. claim 응답·worker 예산 판단·DB 예산 전환·보통 non-hold RETRY delay가 모두 이 값으로 계산한다. hold RETRY delay는 60초다.
  • 보통 검증 RETRY delay(초)는 min(300,2^clamp(budget_attempt_count,0,9))다. 지수 clamp 후 최대512를 integer로 변환한다. min 뒤에 무제한 지수/cast를 두지 않는다. 원 raw31/32가 hold로 증가했어도 해제 후 budget1의 delay는2초다.
  • T7 backoff(초)는 min(21600,300×2^clamp(n,0,7))다. n은 해당 연속 no-change/failure 수다. n 증가는 중간 넓은 정수에서 계산하고31로 포화한다. attempt/row_version처럼 소유권·관측에 쓰는 카운터는 포화해 재사용하지 않는다.
  • 기존 inbox attempt_count 또는 row_version의 표현 한계에서 +1 overflow가 예상되면 claim은 쓰기 전에 NOT_CLAIMABLE로 닫고 COUNTER_LIMIT 운영 경보를 남긴다. terminal REVIEW를 만들지 않는다. 기존 trigger의 old+1 계약은 유지하며 포화 UPDATE로 바꾸지 않는다. T7 attempt·row_version의 표현 한계도 같은 검사·비종결 경보를 쓴다. 한계 경보는 내부 resource UUID와 제한 종류만 포함한다.
  • 증거 의무: raw31/32+hold RETRY 기록 후 non-hold retry, 매우 큰 n·31 포화·지수7 clamp, integer 경계 직전/한계 claim0writes를 검증한다. 예산 분리 때문에 무제한 raw 지수 연산을 실행하지 않는다.

G7. 도달 가능한 capacity 시험 — F-M4

  • 저장 총15행(caller≤8, DB code별≤1 최대7)은 보수 capacity 산술이다. 모든 DB code가 한 호출에서 동시에 발생한다는 뜻이 아니다. v2 V-SIZE/V-ASSERT-CAP의 “33facts+caller8+DB7 동시 수용” 기대를 철회한다.
  • 최대 유효 형태 양성은 raw32, ORDER1+CAPTURE32의 실제 evidence와 유효 caller assertion8이다. category/HTTP/사실/ID 조건이 서로 맞는 ADVERSE fixture로 한다. DB-derived는 그 입력에서 실제 발생한 것만 기대한다. gateway/raw request·정규 저장 request·원자 commit을 각각 확인한다.
  • DB code는 독립 fixture로 검증한다: HTTP_REJECTED(422), UNEXPECTED_HTTP_STATUS(예:302), WORK_BOUND_EXCEEDED(raw33·facts0), CAPTURE_ID_UNPARSEABLE, ADVERSE_WITHOUT_EVIDENCE, CLASSIFICATION_INCONSISTENT, CAPTURE_ID_DIVERGENCE. reachable 조합 예는 CLEAN 요청의 X/Y divergence→CAPTURE_ID_DIVERGENCE+CLASSIFICATION_INCONSISTENT다. 같은 HTTP에서 rejected와unexpected를 함께 기대하지 않는다. 33facts+8caller와 ADVERSE_WITHOUT_EVIDENCE를 함께 기대하지 않는다.
  • 초과22023, native N중1 오류 전체 rollback, 이미 결과 있는 과대 입력 hash-only conflict를 별개 음성으로 유지한다. 실제 fixture의 유효성은 RPC 조건과 독립 literal로 확인한다. runtime 행 수는 미측정이다.

G8. P2 category 닫힌 표 — F-L1

  • 이 표는 P2 전용이다. P1의 NO_RESPONSE 이름을 재사용해 의미를 추정하지 않는다. requested category/kind와 effective kind를 구분한다. 모든 category는 크기·권한·정확 key·evidence 형식 검사와 DB adverse downgrade를 거친다.
  • READ_ORDER_NO_CAPTURE → CLEAN: 2xx PARSED, ORDER fact1, O=[], CAPTURE fact0, receive index null. ORDER의 nominal 상태는 known non-adverse다. 유효 adverse evidence가 있으면 G3에 따라 effective ADVERSE다.
  • READ_CAPTURE_PENDING → CLEAN: 2xx PARSED, ORDER fact+[CAPTURE PENDING], O가 그 ID 포함, bind 최대1, receive index null. READ_CAPTURE_COMPLETED → CLEAN: 같은 구조의 COMPLETED, receive index가 그 CAPTURE를 가리킨다. E/O divergence·native REVIEW·실제 adverse는 DB가 override한다.
  • READ_ORDER_VOIDED → ADVERSE: 2xx PARSED, G3의 ORDER VOIDED fact 또는 정확 partial assertion. READ_ADVERSE_FACT → ADVERSE: PARSED, 실제 표현 가능한 adverse/모순 fact≥1. READ_NON_SUCCESS_FACT → ADVERSE: non2xx PARSED 응답에서 실제 provider fact를 얻었으나 성공 응답으로 볼 수 없는 경우, fact≥1이다. NO_DATA로 사실을 버리지 않는다.
  • READ_CONTRADICTION_UNREPRESENTABLE → ADVERSE: 2xx PARSED, caller assertion≥1. READ_PARTIAL_INDETERMINATE → ADVERSE: 2xx PARSED의 불완전 형태로 CLEAN을 판정할 수 없으며 UNREPRESENTABLE_CONTRADICTION 또는 UNRECORDABLE_PROVIDER_FACT assertion≥1이다. partial parsed 판단을 NO_DATA로 숨기지 않는다.
  • READ_WORK_BOUND_EXCEEDED → ADVERSE: PARSED, raw>32, capture_count_exceeded=true, facts0/O=null. READ_CAPTURE_ID_UNPARSEABLE → ADVERSE: PARSED, unparseable_capture_count>0, bounded 실제 facts만 허용한다.
  • READ_HTTP_REJECTED → ADVERSE: valid HTTP400..499에서408/429/401/403 제외. READ_HTTP_UNEXPECTED → ADVERSE: valid HTTP100..199 또는300..399. DB가 각각 HTTP_REJECTED/UNEXPECTED_HTTP_STATUS를 파생한다. P1 HTTP_UNEXPECTED_STATUS도 같은 범위로 정정한다. HTTP 자체의100..599 밖 숫자는 입력 형식 오류이며 native http_status CHECK를 우회하지 않는다.
  • READ_ADVERSE_UNSPECIFIED → ADVERSE: 다른 범주로 표현할 근거를 만들 수 없는 신뢰된 W의 보수 ADVERSE 판단이다. facts0/caller assertion0도 허용하고 DB가 ADVERSE_WITHOUT_EVIDENCE를 반드시 저장한다. 실제 provider status를 만들어 내지 않는다. late에도 이 범주를 사용할 수 있다.
  • READ_TRANSPORT_UNKNOWN → NO_DATA: http/body null. READ_HTTP_5XX → NO_DATA:500..599, READ_HTTP_408/429/401/403 → NO_DATA:해당 status. READ_BODY_UNREADABLE → NO_DATA:2xx이며 EMPTY/OVERSIZE/INVALID_UTF8/INVALID_JSON/STREAM_ERROR. READ_LOCAL_BUDGET_EXHAUSTED·READ_LOCAL_CANCELLED → NO_DATA:G5의 GET 미시작이다.
  • 모든 NO_DATA는 facts0/assertions0/O=null/unparseable0/exceededfalse이며 실제 provider fact나 이미 관측한 adverse 판단이 없어야 한다. PARSED error 객체만 있고 provider 사실·판단을 얻지 못한 HTTP 실패는 허용한다. 이미 사실/판단을 얻었으면 위 ADVERSE category로 보존한다. OPEN·ABANDONED는 NO_DATA category가 아니다.
  • HTTP 범주가 겹치면 실제 알려진 adverse·VOIDED·raw 초과·unparseable·표현불가 판단이 먼저다. 그 뒤 완전 CLEAN, 그 뒤 “provider fact를 얻지 못한” NO_DATA다. 다른 enum·조합은22023이며 새 default CLEAN은 없다.

G9. 최종 한정 정정 v3.1 — N-M1·N-L1..N-L4

  • N-M1 정규화: 형태가 유효한 단일 purchase_unit에서 payments 또는 captures 키가 없으면 관측 집합 O=[]이다. captures=[]도 O=[]다. null은 purchase_unit/payments/captures의 형태 자체를 판정할 수 없는 경우에만 쓴다. 이 규칙이 기반 5부의 “captures 배열이 없으면 null” 문장보다 우선한다. E=∅인 정상 생략/[]는 READ_ORDER_NO_CAPTURE CLEAN 후보이고, E={X}에서 생략/[]면 DB divergence로 ADVERSE다. 형태 오류는 null로 남겨 partial ADVERSE로 분류하며 CLEAN을 허용하지 않는다. provider 생략 여부는 여전히 UNVERIFIED다.
  • N-L4 정확 집합: CLEAN 세 행 모두 O non-null이며 O는 CAPTURE fact ID 집합과 정확히 같아야 한다. READ_ORDER_NO_CAPTURE는 O=[], 나머지 두 행은 O={그 CAPTURE id}다. O={X,Y}/fact={X}처럼 유효한 부정 데이터가 있으면 형식 검증으로 버리지 않고 DB가 CLASSIFICATION_INCONSISTENT를 파생해 effective ADVERSE로 만든다. E/O 비교는 native bind 전의 locked snapshot에서 E를 고정한다. 원 fact 배열 순서·bind flags·raw request hash를 집합 정규화로 바꾸지 않는다.
  • N-L1 DB 파생: P1/P2의 기존 (d) 중 “200–599 밖→UNEXPECTED_HTTP_STATUS”를 폐기하고 “유효 HTTP100..199 또는300..399→UNEXPECTED_HTTP_STATUS”로 바꾼다. category 이름과 무관하게 같은 구조 status에서 파생한다. 302 기대는 DB RPC 직접 입력의 검증 fixture이며 redirect:'error'인 실제 W fetch에서 302가 노출된다고 주장하지 않는다. W transport의 redirect 오류는 기존 TRANSPORT_UNKNOWN이다.
  • N-L2 provider·버전: 신규 claim_web_payment_purchase_v2는 PayPal과 PortOne을 포함한 모든 WEB_PURCHASE_V2 provider를 처리하고 같은 트랜잭션에서 T10을 기록한다.   • N-L3 카운터 경보: COUNTER_LIMIT에서 claim은 대상 상태·증거·경보에 0 writes다. 검증 list/claim과 queue claim의 후보 술어에서 표현 한계 행을 제외해 첫 항목 반복 선택을 막는다. health 평가자가 원천 inbox/queue 카운터와 order 연계를 읽어 web-payment:counter-limit:<order_id> 경보를 만든다. resource_type은 기존 허용 web_payment_order, resource_id는 내부 order UUID, basis_kinds에는 COUNTER_LIMIT_INBOX_ATTEMPT/COUNTER_LIMIT_INBOX_VERSION/COUNTER_LIMIT_QUEUE_ATTEMPT/COUNTER_LIMIT_QUEUE_VERSION 닫힌 enum을 추가한다. provider ID·inbox ID·사용자 ID·오류 원문은 details에 넣지 않는다. 기존 경보 namespace 제한과 해소 규칙을 유지한다.
  • 추가 증거: 유효한 captures 키 없음/[]/형태 오류 × E=∅/{X}의 6조합, CLEAN singleton과 추가 ID, 302 RPC 파생, 새 worker의 PayPal/PortOne v2 claim과 구 PortOne 응답 보존, 한계 후보 제외·claim0writes·health 경보를 각각 검증한다. 이 시험들은 아직 STATIC이다.

1. 크기 측정 정의(Q-M1)

  • canonical octets(x) := octet_length(convert_to(x::text,'UTF8')). jsonb::text는 PostgreSQL의 결정적 정규 출력이다. 요청 상한과 저장 CHECK는 모두 이 값을 쓴다.

4. 후보 claim·finish(D, service_role)

  • claim_web_payment_reconciliation_item(p_executor_id uuid, p_lease_seconds integer 30..180) returns jsonb: E에서 next_due_at, order_id 순 1건을 FOR UPDATE SKIP LOCKED로 고른다. hold.get_eligible을 같은 함수 안 별도 문장에서 다시 확인한다. lease_token 갱신, attempt+1, row_version+1. 그리고 비관적 backoff로 next_due_at := now + min(5분×2^consecutive_failures, 6시간)을 미리 설정한다. 그래서 process가 죽어 finish가 없어도 같은 첫 항목이 다음 run에서 맨 앞에 다시 오지 않는다(첫 항목 기아 방지). 반환 user_id는 DB의 order 소유자다. executor는 이 값만 actor로 쓴다.
  • finish_web_payment_reconciliation_item(p_order_id uuid, p_lease_token uuid, p_result_code text) returns jsonb: lease_token이 같아야 한다(다르면 STALE_LEASE, 쓰기 0). result_code(닫힌 집합)와 효과:

- INTAKE_PENDING → DONE.
- HELD → HELD(hold 재계산).
- NO_CHANGE(CLEAN 무capture·PENDING·NO_RESPONSE 유지) → next_due = now + min(5분×2^consecutive_no_change, 6시간), consecutive_no_change+1.
- NO_DATA → 같은 backoff, consecutive_failures+1.
- CREDENTIAL_UNAVAILABLE(closed resolver·token 실패, cycle 없음) → 같은 backoff, consecutive_failures+1.
- IN_PROGRESS(READ_IN_PROGRESS) → next_due = now+1분.
- DEFERRED(budget 부족으로 open 전 반환) → next_due = now, 카운터 불변.
- FAILED(그 밖) → backoff, consecutive_failures+1.

  • backoff 상한 6시간, 5분 기본은 설계자 제안이다(R7: 5분 호출 주기와 별개, 제안).

  • 항목 처리 순서: claim(1건) → owner(getChargeContext) → prepare replay → binding → credential → token → [open 판단] → open → GET → complete → finish.
  • 읽기 hard cancellation: credential·token·GET 각 provider/resolver 읽기에 signal := AbortSignal.any([run signal, timeout(min(10초, hardDeadline − now − 25초 reserve))])를 넘긴다. 남은 시간이 0 이하이면 그 읽기를 시작하지 않는다.
  • open 판단: hardDeadline − now ≥ 25초(GET 10초 + complete 10초 + finish 5초)일 때만 open한다. 아니면 finish DEFERRED(lease 반환, cycle 없음). open 뒤에는 GET을 반드시 시도한다. 취소된 GET은 TRANSPORT_UNKNOWN이고 complete NO_DATA다.
  • 시작한 write(open, complete, finish, run 기록)는 Promise.race로 버리지 않고 끝까지 await한다(D 규칙과 같다, web-purchase-worker.ts:147-150). DB RPC 자체의 10초 timeout(repository.ts:180)은 유지한다. write 응답 유실은 “commit 불명”이다. complete 불명이면 cycle은 기한 뒤 ABANDONED가 된다(C 비용).
  • 항목마다 GET은 최대 1회다. claim·intent·CREATE·capture POST는 0이다.
  • run 기록: 시작 시 record_web_payment_reconciliation_run(phase STARTED), 끝에 FINISHED와 metrics. metrics 정확 정수 key: claimed, opened, completed_clean, completed_adverse, completed_no_data, held, deferred, credential_unavailable, in_progress, failed, read_cancelled, write_unknown, oldest_due_lag_seconds. result_code ∈{OK, PARTIAL_BUDGET, DISCOVERY_FAILED, WRITE_FAILED, CREDENTIAL_UNAVAILABLE}. FINISHED 기록 실패 → route 503과 로그. health가 STARTED-without-FINISHED를 잡는다.
  • platform kill(open 뒤 complete 전) → ABANDONED → absence 보류. C의 비용이며 경보로 드러난다.
  • app/api/internal/payment/paypal-reconciliation/route.ts: POST만, 내부 secret header, 응답은 숫자 요약뿐. closed resolver로만 조합한다. 배포·secret·호출 주기(5분 제안)·pg_net timeout(60초 이상 필요)은 OG2다.
