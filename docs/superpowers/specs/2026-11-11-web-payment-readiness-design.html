PayPal과 PortOne을 함께 준비하고, 준비된 수단부터 개방한다

사용자가 순차 개방과 운영자 확인 후 결제사 콘솔 환불을 선택했다. Astra/high의 계약 조사와 Fable 5.2/high의 재검토를 마쳤으며 기술설계는 통과했다. 재검토의 추가 권고 5건은 조정자가 소스와 대조해 문서에 반영했다. 이 보완 문장들은 세 번째 독립 리뷰를 받지 않았다. 사용자 설계·사업 정책 승인과 운영 개방은 별도다.

확정된 범위: 글로벌 PayPal과 국내 PortOne 웹결제를 준비한다. 가상화폐는 다음 단계로 미룬다. 두 수단을 함께 준비하되 실제 개방은 준비 조건을 충족한 수단부터 진행한다.

준비 완료의 의미: 주문·결제·지갑 적립의 계약, 국내·글로벌 화면, 실패 복구, 테스트 기준, 결제사 심사·환경 설정 자료를 검토 가능한 상태로 만든다. 단순히 버튼을 켜는 작업으로 끝내지 않는다.

1. 선택한 방식과 기존 근거

방식장단점결정
두 수단 동시 개방동시에 같은 구매 경험을 제공하지만 한 결제사의 심사 지연이 전체 개방을 막는다.선택하지 않음.
두 수단 준비 후 각각 순차 개방공통 계약과 화면을 함께 검증하고, 준비된 수단부터 개방한다. 공급자별 가용성과 중지 제어가 필요하다.사용자 선택. 어느 수단이 먼저인지는 준비 결과로 결정한다.
모든 수단 표시 후 공급자에서 거절사용할 수 없는 수단으로 진입해 결제 실패와 통화 혼동을 만든다.선택하지 않음.

과거 코드·메일·콘솔 관측과 출처는 웹결제 재개 조사 보고서에 있다. 2026-11-11 관측에서 PortOne은 실연동 채널 0개, PayPal은 운영 앱이 있지만 웹훅과 웹 운영 변수 연결이 미완료다. 현재 어느 수단도 즉시 일반 개방 가능한 상태로 판정하지 않는다.

PayPal은 직접 연동을 유지하고 국내 결제는 PortOne V2를 사용한다. PayPal을 PortOne으로 이전하거나 새로운 PG를 추가하는 작업은 이번 범위에 없다. 기존 KG이니시스·카카오페이 신청의 재개 조건을 우선 확인한다.

2. 공통 주문·결제·적립 계약

브라우저는 상품·결제수단·결제 국가/지역과 중복 방지용 요청 식별자만 전달한다. 서버가 로그인·탈퇴·시험 권한, 공급자와 환경의 개방 여부, 지원 통화·상품을 검사하고 금액과 지급량을 확정한다. 클라이언트가 보낸 가격·별사탕·사용자 ID를 권한이나 적립 근거로 사용하지 않는다.

항목준비할 계약
주문과 견적picnic-supabase에 영속적인 서버 주문·불변 견적과 공급자 ID 연결 계약을 추가한다. 결제창 진입 전에 소유자, 공급자, 환경, 상품, 통화, 법정화폐 최소단위 금액, 기본 별사탕·상품 보너스 지급량, 보너스 정책 버전과 만료 계산 기준을 보존한다. 공급자 주문 ID와 실제 결제 ID의 대응을 보존하고 워커가 이 주문을 읽어 검증·지급한다. 적립 시점의 기존 snapshot만으로 대신하지 않는다.
견적 유효기간기술 제안: 견적 발급 후 15분까지 새 결제창 진입과 서버의 최초 capture/수동 승인 요청을 허용한다. 공급자 주문 연결만으로 이 기한을 없애지 않는다. 기한 뒤에는 새로운 청구 POST를 보내지 않고 공급자 조회로 기존 시도의 결과만 확인한다. 기한 안에 보낸 요청이 늦게 완료되면 고정한 금액·지급 약속을 이행한다. 이미 납부한 주문은 웹훅·적립 지연 때문에 만료시키지 않는다. 미청구·종결을 확인한 뒤에만 새 견적을 발급한다.
적립서버·워커가 공급자 원본에서 실제 capture의 COMPLETED 또는 PortOne PAID, 계정·상점·허용 채널·시험 여부, 환경, 통화·금액, 주문 소유자와 상품을 검증한다. 현재 상품의 변경된 가격·지급량 대신 확정 견적을 검증·지급한다. 상점·채널·시험 여부를 확인하지 못한 거래는 적립하지 않고 운영 확인 상태로 보존한다. 한 거래의 적립은 한 번만 발생해야 한다.
메타데이터새 계약 v2는 짧은 v2:<서버 주문 UUID> 참조로 연결한다. 서버 주문이 소유자·상품·견적의 권위 근거이며 ID만으로 접근을 허용하지 않는다. 웹과 워커를 함께 변경하고 공급자 원본의 참조·실제 거래 ID를 대조한다. 현재 camelCase/snake_case 불일치는 v2 경로와 과거 호환 경로를 분리해 해소한다. 과거 주문은 생성 시점·공급자 원본·원지급 근거로만 연결하며 임의 키 혼용을 허용하지 않는다.
중복과 재시도공급자·환경·실제 거래 ID에 대한 영속적인 중복 방지와 원자적 적립을 유지한다. 동일 주문 재호출은 권한을 확인한 현재 상태를 반환한다. 결제 성공 후 응답 유실·접수 실패는 같은 주문을 조회·재접수하여 복구한다. 새 결제를 다시 만들지 않는다.
상태 조회사용자는 자신의 주문만 조회한다. 공급자 원본·메타데이터·운영 오류 원문을 노출하지 않는다. 적립 처리 중, 재처리 대기, 운영 확인 필요를 구분하고, 요청 소유자·공급자·환경 조건을 함께 적용한다. 관리자 재처리 권한은 사용자 재조회 권한과 분리한다.
이미 청구된 과거 주문현재 주문 스냅샷이 없다는 이유로 존재를 숨기거나 재결제를 권하지 않는다. 검증 가능한 과거 근거로 복구하고, 근거가 부족하면 운영 확인 대상으로 남긴다. 원래 지급 약속을 확인하지 못한 상태에서 현재 상품량으로 임의 적립하지 않는다.

위 15분은 조정자의 제안이며 사용자 확정값이 아니다. 현재 상품 가격·별사탕·보너스·환불 약관을 임의로 바꾸지 않는다. 서버 주문·불변 견적·워커의 견적 검증과 지급은 직원 시험을 포함한 첫 운영 청구 전 선행 조건이다. 제한 개방도 예외가 아니다. 그 전에는 mock과 운영에서 격리된 공급자 시험만 수행한다.

접수 전 상태와 프로모션

공급자 상태를 서버 주문에 먼저 보존한다. PayPal 주문 수준의 COMPLETED만으로 구매 inbox에 접수하지 않는다. 하위 capture가 PENDING이면 “결제 확인 중”으로 유지하고 웹훅·주기 조회로 확인한다. COMPLETED로 바뀐 후 같은 capture ID로 접수한다. DECLINED/FAILED는 공급자 확인 후 실패로 종결한다. 조회 오류·미확인·보류를 실패나 취소로 추정하지 않는다. PortOne도 PAID 이전에는 구매 inbox에 넣지 않는다. 환불·취소 상태는 아래 환불 경로로 보낸다.

접수 직후 상태가 바뀌는 경쟁도 처리한다. 워커가 재조회한 상태가 보류이면 주문에 대기 상태를 남기며 영구 DEAD로 종결하지 않는다. 환불·취소를 확인하면 구매 처리와 같은 주문 잠금 아래 환불 조정 상태로 전환한다. 환불과 지급의 순서를 직렬화하되 외부 공급자 상태와 DB 트랜잭션이 원자적이라고 가정하지 않는다. 뒤늦은 환불은 지급 결과에 맞춰 회수한다.

상품 보너스는 견적의 보장 지급량에 포함한다. CANDY_BOOST_DAY는 별도 조건부 프로모션으로 둔다. 주문에는 적용할 프로모션 정책 버전과 조건을 고정하고 공급자가 증명한 실제 결제 완료 시각으로 자격을 평가한다. 확정 전에는 보장 합계에 더하지 않는다. 완료 시각 미확인은 프로모션 확인 중으로 표시한다. 현행 워커의 현재 정책 재평가와 PayPal create_time 사용을 그대로 보장 근거로 쓰지 않으며, 정책 버전·완료 시각 검증 계약을 DB/워커 변경에 포함한다. 첫 개방에서 이 계약을 못 맞추면 프로모션을 임의 제외하지 않고 개방을 보류한다.

공급자의 완료 시각을 처음 검증할 때 주문에 한 번 저장한다. 함께 검증 출처·이벤트/거래 ID·원본 해시와 서버 관측 시각을 기록하되, 서버 관측 시각을 결제 완료 시각으로 대신하지 않는다. 나중에 바뀐 update_time이나 재조회 시각으로 덮어쓰지 않는다. 완료 시각을 증명할 수 없거나 후속 증거와 충돌하면 프로모션 확인 상태로 보존한다. 기본 지급과 후속 프로모션 워커가 같은 불변 증거를 사용하도록 기존 시각 검증 계약을 보완한다.

보장 지급량과 잔액 증가를 구분한다. 견적의 기본 별사탕·상품 보너스는 기존 회수 채무를 상계하기 전 총지급량이다. 워커는 총지급량으로 견적을 검증한다. 본인 상태 조회와 완료 화면에는 통화별 총지급량, 채무 상계량, 실제 잔액 증가량을 따로 제공한다. 현재 결과 DTO만으로는 상계 상세가 부족하므로 소유권 검증된 배분 결과 조회를 추가한다. 앱 환불에서 생긴 기존 채무도 상계될 수 있다. 결제 전에는 해당 정책과 현재 예상 상계량을 알리고, 대기 중 다른 거래로 바뀔 수 있는 예상값과 적립 시 확정값을 구분한다. 웹 환불의 새 채무 생성과 기존 채무 상계·고지의 사업 승인은 각각 필요하다.

PayPal 공식 capture 상태는 PENDING·COMPLETED·실패·환불을 구분한다. 이 설계는 개별 capture 상태를 기준으로 한다. 최신 주문 custom_id 규격은 최대 255자다. 현재 웹의 127자 검사는 별도 코드 제한이며, 공급자 규격과 혼동하지 않는다. 새 참조는 39자 ASCII이므로 두 제한보다 짧다.

3. 두 결제수단의 구현 준비

PayPal · 글로벌 · USD

  1. 서버 주문과 PayPal 주문을 연결하고 요청별 멱등 키를 보존한다.
  2. 공식 SDK의 승인·취소·오류 흐름을 사용한다. 팝업이 닫혔다는 사실만으로 capture를 시작하지 않는다.
  3. capture 전에 주문 소유자, 판매자·환경, 서버 견적과 공급자 주문의 금액·통화를 대조한다.
  4. capture 결과의 하위 capture ID와 상태를 저장한다. PENDING은 대기하고 COMPLETED만 구매 접수한다. 주문 ID와 혼동하지 않는다.
  5. 검증 가능한 웹훅과 서버 재조회를 같은 접수·적립 경로에 연결한다.
  6. 접수 응답에는 처리 중 상태를 표시하고 실제 적립 완료 후 성공 화면을 표시한다.

PayPal 멱등성 안내의 요청 ID 재사용 조건을 적용한다. API별 지원 여부와 보존 기간도 확인한다. 공식 웹훅 안내에 따라 앱·환경별 Webhook ID와 서명을 검증한다.

PortOne · 국내 · KRW

  1. 서버가 결제 ID와 금액·상품·허용 채널을 정하고 주문에 보존한다.
  2. 브라우저 SDK 요청에 서버가 확정한 값을 사용한다. 기술 제안: 대상 채널에 수동 승인을 적용하고, 서버가 주문·소유권·견적·개방 상태를 확인한 뒤 승인한다.
  3. 데스크톱 응답과 모바일 리다이렉트를 같은 상태 조회 흐름으로 연결한다.
  4. 웹훅 서명을 검증한 뒤 결제 조회 API로 실제 금액·통화·상점·채널을 재검증한다.
  5. 웹·채널·워커의 테스트/운영 환경을 명시적으로 맞춘다. NODE_ENV를 결제 환경의 근거로 사용하지 않는다.
  6. 웹훅과 브라우저 응답 순서가 바뀌어도 같은 주문에 한 번만 적립한다.

공식 수동 승인 안내는 채널별 활성화와 서버 승인 API를 설명한다. 실제 KG이니시스·카카오페이 채널의 지원·활성화를 확인하고 시험한다. 수동 승인을 사용할 수 없으면 자동 승인으로 몰래 전환하지 않고, 사후 검증·취소/환불의 한계를 별도 설계로 검토한다. 기존 cookie 인증 /api/payment/portone/confirm은 PG가 호출하는 서명 검증 컨펌 웹훅과 같지 않다.

현재 SDK 성공 조건의 response.code === null도 점검한다. 공식 성공 응답 예시는 실패 코드가 없는 경우를 사용하므로 null만 인정하는 시험으로 끝내지 않는다. 공식 웹훅 안내는 브라우저 응답과 웹훅의 순서가 보장되지 않음을 설명한다.

4. 국내·글로벌 화면과 복구

언어는 표시 설정이다. 결제 국가/지역, 회원 국적, IP 위치, 공급자 계정 국가는 서로 다르다. 국가 미확인을 글로벌 적격으로 처리하지 않는다. 사용자는 결제 국가/지역을 확인·변경할 수 있고 서버는 해당 공급자·상품·통화의 허용 범위를 검사한다. 사용자의 국가 선택만으로 공급자의 실제 계정 제한을 충족했다고 보지 않는다.

초기 설계는 사용자가 확인한 ISO 국가 코드를 주문의 billing_country로 보존한다. 언어·IP·시간대는 추천값이며 권한 근거가 아니다. 서버의 버전 있는 공급자/국가/통화 허용 목록을 주문 생성과 청구 전에 검사한다. 초기 국내 경로는 KR+PortOne+KRW이며 KR을 선택한 사용자의 PayPal 신규 주문을 서버에서도 거부한다. 글로벌 PayPal+USD는 계약으로 확인한 국가만 허용한다. 확인 전 허용 목록은 비워 둔다. 국가 변경은 미청구 주문을 새 견적으로 전환하며 이미 청구된 주문의 국가를 바꾸지 않는다. 공급자가 제공하는 국가 정보가 선택값과 충돌하면 청구를 보류한다. 계정 국가를 공급자가 제공하지 않으면 확인했다고 주장하지 않고 공급자의 거래 적격성 심사를 따른다.

서버는 공급자·환경별 신규 주문과 추가 청구 허용 여부를 검사한다. 중지 후에는 미청구 주문의 새로운 청구를 막고, 이미 청구된 주문의 조회·적립·웹훅·환불을 계속 처리한다. 중지 직전에 승인된 요청과 도착이 늦은 결제 통지도 같은 계약으로 복구한다. 화면 스위치나 관리자 버튼 제한을 서버 제어의 대체물로 쓰지 않는다.

개방 제어와 누락 주문 탐지

공급자·환경별 개방 상태, 신규 주문/청구 허용, 국가·통화·채널 허용 목록, 내부 시험·제한 개방의 사용자 ID 목록을 DB의 서버 전용 설정으로 관리한다. 기본값은 닫힘이다. 첫 버전은 관리자 권한을 검사하는 서버 명령/RPC와 변경 사유·버전·감사 기록을 제공하고 별도 관리 화면은 만들지 않는다. 브라우저는 공개 가능한 가용성만 받는다. 주문 생성과 외부 청구 직전에 서버가 최신 설정을 읽고, 조회 실패 시 신규 청구를 막는다. 화면 캐시가 서버 검사를 대신하지 않는다. 이미 외부로 보낸 청구 요청은 중지 이후 결과를 수집·복구한다. 중지로 이미 승인된 외부 동작을 소급 취소했다고 표시하지 않는다.

서버 주문은 공급자 호출 전에 저장하고 요청 키를 고정한다. picnic-supabase의 주기 대사 작업은 미종결 주문, capture/승인 시도 후 결과 미확인 주문, 접수 실패 주문을 공급자에서 재조회한다. 기본 주기는 5분으로 제안하며 API 한도에 맞춰 지연·동시성·재시도 간격을 제한한다. 호출 응답 유실은 저장한 요청 키·공급자 조회/대사 근거로 복구하고 새 주문으로 청구하지 않는다. 공급자 ID를 아직 얻지 못한 주문도 별도 경보로 남긴다. 15분 이상 갱신되지 않은 청구 시도·결제 완료 후 미접수와 재시도 소진을 운영 경보로 삼되, 공급자 보류는 실패로 단정하지 않는다. 기존 inbox 경보만으로 이 기능을 대신하지 않는다.

환불 문의·환불 요청·분쟁이 열린 주문은 적립 완료 뒤에도 대사를 계속한다. 이 목록 밖의 완료 주문도 일별 거래/정산 대사에 포함해 환불 웹훅 유실과 콘솔 밖의 자금 회수를 탐지한다. 조회 범위는 공급자별 환불·분쟁 가능 기간과 API 조회 보존 기간을 확인해 설정하며, 미해결 건은 기간 밖에서도 유지한다. 공급자 API의 조회 범위가 부족하면 승인된 정산 보고서 대사 절차로 보완한다. 이 운영 절차가 없으면 해당 공급자를 개방하지 않는다.

첫 범위에서 분쟁·차지백·역결제는 서명/원본 검증, 영속 접수, 주문 연결, 운영 경보와 담당자 조치 기록까지 지원한다. 일반 환불로 자동 치환해 회수하지 않는다. 운영자가 이중 환불·중복 회수를 확인해 조치하고 최종 자금 상태와 지갑 조정 결과를 기록한다. 자동 회수 정책은 후속이다. PayPal 공식 이벤트 목록의 PAYMENT.CAPTURE.REVERSED 및 분쟁 이벤트와 PortOne 분쟁 이벤트를 대상 채널의 실제 지원 범위와 대조한다.

첫 개방의 환불·탈퇴 처리

사용자 선택: 문의 접수 → 운영자 확인 → 결제사 콘솔에서 환불한다. 회원 직접 자동 환불과 새 환불 승인 화면은 첫 범위에 없다. 웹 상태 동기화·지갑 회수는 첫 개방의 필수 기능이다. 문의 번호와 서버 주문을 연결하고 운영자는 원결제·현재 적립·소비·기존 환불·처리 중인 작업을 확인한다. 콘솔 요청만으로 완료 처리하지 않고 공급자의 최종 환불 결과를 검증한다.

  • 아직 지급하지 않은 전액 환불은 구매를 적립하지 않고 환불 완료로 종결한다. 구매 inbox가 이미 있으면 같은 주문 잠금과 버전 검사로 지급을 막고 새 종결 계약으로 처리한다. 존재하지 않는 snapshot을 요구하는 기존 환불 worker로 보내지 않는다.
  • 미적립 상태의 부분환불은 첫 버전에서 자동 잔여 적립을 하지 않는다. 운영자는 원칙적으로 적립 상태를 먼저 정리한 뒤 부분환불을 시작한다. 외부에서 부분환불이 먼저 발생하면 구매와 환불을 운영 확인 상태로 보존하고 담당자에게 알린다. 운영자가 원결제·환불액·원지급 부재를 확인하고 고객과 잔여액 환불 또는 검증된 지급 수리를 결정한다. 지급 수리는 원지급 snapshot 생성과 보존한 환불 누적액의 적용을 같은 잠금·트랜잭션으로 묶어, 환불을 적용하지 않은 전량을 사용 가능 잔액으로 노출하지 않는다. 고객에게 재결제를 요청하지 않고, 처리 담당·기한·문의 번호를 남긴다. 담당자를 개방 전에 지정하고 1영업일 내 첫 확인을 기본 운영안으로 제안하되, 공급자 응답 기간을 환불 완료 기한으로 약속하지 않는다. 이 경로와 수리 권한은 개방 전 시험한다.
  • 이미 지급한 주문은 기존 snapshot과 검증한 누적 환불액으로 회수한다. 기본 별사탕/상품 보너스 비례 회수·프로모션 보너스 전액 회수·부족분 채무를 웹에 적용할지는 사업 정책과 약관 대조 후 확정해야 한다. 문의/콘솔 방식의 승인은 이 회수 정책의 승인과 다르다.
  • 청구 뒤 탈퇴했고 아직 지급하지 않은 주문은 신규 적립을 막고 운영자 환불 대상으로 보존한다. 탈퇴 상태를 이유로 서명 검증된 이벤트 접수를 403으로 버리지 않는다. 먼저 영속 접수한 뒤 운영 확인으로 전환한다. 탈퇴 전에 이미 지급한 주문은 승인된 회수 정책을 따르며, 탈퇴 여부와 지급·환불 조정은 같은 주문 잠금 아래 확인한다.

사용자 승인에 제시할 범위

구현 제안은 격리 환경 검증 → DB 주문·견적·워커·대사 → PayPal·PortOne 어댑터 → 본인 상태/환불 화면 → 통합 시험 순서다. PortOne 어댑터는 대상 채널의 수동 승인 지원 확인을 선행 조건으로 둔다. 미지원이면 해당 공급자의 설계를 다시 검토하며 PayPal 준비는 계속한다. 새 유료 환경·서비스 비용이 필요하면 실제 견적을 만든 뒤 별도 승인을 받는다.
