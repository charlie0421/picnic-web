3. 지금의 동작 — 전제로 삼을 것

요청이 처리되는 순서

  1. vercel.json: picnic.fan 을 https://www.picnic.fan 으로 보낸다(이것만 영구 리다이렉트다).
  2. next.config.js 의 redirects(): / → /en/vote, /{정규 언어} → /{언어}/vote, 종료된 서비스 주소(goong-hap·community·pic·novel 등) → 투표·마이페이지, /download.html, /privacy_en.html·/privacy_ko.html. 전부 307이고 middleware 보다 먼저 실행된다.
  3. middleware.ts: ① 언어 접두어 판정(아래 표) → ② 인앱 브라우저면 /open-in-browser 안내로 → ③ Supabase getClaims 로 세션 갱신·검증 → ④ 로그인 사용자의 탈퇴 여부 확인.
  4. 라우트: app/[lang]/…(언어 페이지), app/(bare)/…(언어 밖: 인증 콜백·로딩, 광고 플레이어, 리다이렉트 스텁), app/api/…, 그리고 없는 경로를 404 로 받는 catch-all 다섯 개.

인증과 탈퇴 계정

  • middleware 는 supabase.auth.getClaims() 로 세션을 갱신·검증한다. ES256(JWKS) 토큰은 Auth 서버 왕복 없이 로컬에서 검증하고, 그 밖의 토큰은 SDK 가 getUser() 로 폴백한다. 비로그인 요청은 네트워크 호출이 없다.
  • 로그인 사용자가 로그인 페이지가 아닌 경로를 요청하면 user_profiles.deleted_at 을 조회한다. 탈퇴 계정이면 로그아웃시키고 /{언어}/login?error=withdrawn 으로 보낸다. 조회가 실패하면 통과시킨다.
  • 결제·스토리지·업로드·지갑·투표 제출·QNA·프로필·세션 API 는 isWithdrawnUser(lib/supabase/server.ts)로 탈퇴 계정을 따로 막는다. 이쪽은 조회 실패 시 막는 쪽(fail-closed)이다.

5. 지켜야 할 것

건드리면 안 되는 것

감사 계획 docs/audit-2026-09-26/plan.md §6 에 23개 항목이 있다. 작업 전에 읽는다. 그 가운데 자주 걸리는 것과 이 세션에서 새로 생긴 것만 적는다.

  • DB 스키마·RLS·RPC 는 picnic-supabase 레포 소유다. 이 레포에 마이그레이션을 추가하거나 supabase db push 를 실행하지 않는다.
  • QNA 와 /media 는 삭제 대상이 아니다. 삭제 범위의 기준은 next.config.js 의 redirects() 목록이다.
  • 새 페이지를 추가하거나 렌더링 모드를 바꾸면 scripts/rendering-modes.js 를 같이 고친다. 안 고치면 테스트와 배포가 실패한다.
  • 서버 컴포넌트에서 headers()·cookies() 나 x-locale 헤더를 읽지 않는다. 읽는 순간 그 페이지가 동적 렌더링이 되어 ISR 이 깨진다. <html lang> 은 [lang] 파라미터로 정한다.
  • public/ 에 파일·디렉터리를 추가하거나, app/(bare)/ 에 페이지를 추가하거나, rewrite 를 추가하면 middleware 의 matcher 와 lib/i18n/locale-routing.ts 의 통과 목록을 같이 고친다. 빠뜨리면 그 경로가 /{언어}/… 로 가서 404 가 된다. __tests__/middleware/pass-through-sync.test.ts 가 실패로 알려 준다.
  • 새 리다이렉트는 307 로 둔다. 영구 리다이렉트(308)는 브라우저에 남아 Instant Rollback 으로 되돌릴 수 없다. __tests__/next-config-redirects.test.ts 가 막는다.
  • ISR 페이지의 조회 실패를 폴백으로 바꾸지 않는다. 실패 화면이 캐시된다.
  • 사이트의 referrer 정책을 origin·no-referrer 로 바꾸지 않는다. 사이트 안의 접두어 없는 이동이 보던 언어로 도착하는 것이 Referer 신호 덕분이다.
  • 결제 테스트의 it.fails 6개를 지우지 않는다. 결함을 고치는 PR 에서 it 으로 바꾼다.
  • plan.md §6 의 13번이 가리키는 스텁 페이지는 #103 에서 app/(bare)/ 아래로 옮겨졌다(app/page.tsx 는 없다).

이 세션에서 굳어진 일하는 방식

  • 사소하지 않은 변경은 형제 워크트리에서 하고 PR 로 올려 squash 머지한다. 머지는 사용자가 승인한 뒤에 한다(문서만 바꾼 기록 PR 은 조정자가 머지하고 보고했다).
  • 고위험 변경(middleware, 인증, 결제, 권한)은 구현과 다른 공급자가 교차 리뷰한다. 이 세션은 Claude 가 구현하고 Codex(gpt-6-sol, high, 읽기 전용)가 리뷰했다. 저위험 PR 은 사용자 선택으로 리뷰 없이 머지했다.
  • 머지 전에 Production 기준선을 찍고, 배포가 끝나면 같은 요청을 다시 보내 비교한다. 결과는 문서 PR 로 설계서와 감사 계획에 기록한다.
  • 테스트를 먼저 쓰고 실패를 본 뒤 구현한다.

항목어떻게 확인하나언제
언어 라우팅 24시간 지표 Vercel 런타임 로그(Production, level error, requestPath 로 묶음, 24시간)에서 /download/vote(머지 전 67건), /favicon.ico/vote(17), /login/vote(9), /apple-touch-icon.png/vote(4)가 0 이 됐는지 본다. statusCode 404 묶음에서 /{언어}/download/vote·/{언어}/login/vote 가 하루 20건을 넘으면 복구 규칙을 넣는다. 기준은 설계서 §6.4 10-02 23:30 KST 무렵. 로그 보존이 약 하루다
로그인 상태 흐름 실제 계정으로 Production 에서: OAuth 로그인과 콜백 뒤 이동, 로그아웃, 토큰 만료 뒤 재방문, 탈퇴 계정 차단, 로그인 상태의 언어 전환, ISR 페이지 위의 로그인 표시 가능한 한 빨리. 자동화로는 할 수 없다. 계정이 없으면 사용자에게 확인을 요청한다
로그인 사용자의 user_profiles.language #109 뒤로 더는 기기 언어로 덮어쓰이지 않는지. 쿠키 쓰기와 같은 조건문 안의 코드라 함께 건너뛴다는 것까지만 확인했다 위와 함께
성능 수치 모바일 Lighthouse LCP 재측정(#93 뒤), Vercel 로그의 middleware 지연과 Auth 요청 수(#95 뒤), 투표 detail API 의 CDN HIT 비율과 폴링 호출량(#84 뒤). 명령은 plan.md §7.3 정해지지 않음
Vercel 캐시 퍼지와 Instant Rollback Production 에서 실제로 실행해 본 적이 없다. Instant Rollback 뒤 다음 배포가 Production 도메인에 자동으로 붙는지도 확정하지 못했다 필요할 때
새 배포가 옛 데이터로 프리렌더되는가 1시간 안에 Production 배포가 두 번 있으면 두 번째 빌드가 앱 버전을 다시 조회하는지 Supabase edge 로그로 본다. 설계서(ISR) §9.2 배포가 연속될 때

설계가 알고도 받아들인 한계는 언어 라우팅 설계서 §6.5 와 §9 에 있다. 대표적인 것: /_next/·/_vercel/ 아래의 조작된 주소는 404 지만 페이지 코드가 실행된다, 없는 번호의 /sitemap-N.xml 이 정적 404 항목으로 남는다, 인앱 브라우저에서 접두어 없는 주소의 이동이 한 번 늘었다.

10. 롤백과 긴급 조치

상황조치
배포 뒤 문제가 보인다 Vercel Instant Rollback(대시보드 또는 vercel rollback <이전 배포 URL>). 빌드 없이 이전 배포로 돌아간다. 이 세션의 리다이렉트는 전부 307 이라 브라우저에 남는 것이 없다. 롤백 뒤에는 다음 배포가 Production 도메인에 붙는지 대시보드에서 확인하고, 안 붙으면 vercel promote <배포 URL>
git revert 로 되돌리려 한다 새 빌드가 필요하고 빌드는 Supabase 조회에 의존한다. Supabase 장애 중에는 revert 빌드도 실패할 수 있으니 그때는 Instant Rollback 을 쓴다
언어 라우팅(#107)을 즉시 되돌려야 하는 신호 통과 목록의 경로(/auth/callback, /auth/loading, /api/banners, /robots.txt 등)가 307·404 가 된다 · public/ 의 실제 파일이 404 텍스트를 돌려준다 · 같은 경로의 307 이 반복된다 · /api/auth/exchange-code·/api/auth/callback 의 오류 비율이 는다. 설계서 §6.3
ISR(#103)을 되돌려야 하는 신호 /{언어}/(rewards|faq|notice|download) 의 5xx 증가, 로그인 실패 신고, 페이지가 옛 내용에 굳어 있음
잘못 올린 공지·리워드를 즉시 내려야 한다 Vercel 캐시 퍼지(vercel cache purge 또는 대시보드의 CDN Cache·Data Cache 퍼지). 그대로 두면 최대 5분(리워드 목록은 60초) 남는다
렌더링 모드 검사가 배포를 막는다 의도한 변경이면 scripts/rendering-modes.js 의 선언을 고친다. 긴급 우회는 환경변수 SKIP_RENDERING_MODE_CHECK=1
폴링 5초가 문제다 투표 상세 fetcher 의 pollingInterval 값을 1000 으로 되돌린다

12. 함정

머지가 곧 Production 배포이고, 문서만 바꾼 머지도 빌드를 돌린다. 빌드가 Supabase 조회에 의존하므로 문서 PR 의 빌드도 실패할 수 있다(#104 가 그랬다). 실패하면 이전 배포가 유지된다. Preview 배포는 없으므로 “Preview 에서 확인” 절차는 성립하지 않는다.

로컬 next build·next start 의 오류가 운영 Sentry 에 들어간다. .env.local 의 DSN 으로 environment: production 이벤트가 간다. 로컬 빌드와 실행에는 SENTRY_DSN= NEXT_PUBLIC_SENTRY_DSN= 를 붙인다. NEXT_PUBLIC_* 는 빌드 때 인라인되므로 빌드에도 붙여야 한다. Sentry 신규 이슈가 Production 것인지는 os.name 으로 구분한다(로컬은 macOS).

워크트리에서 메인 폴더의 node_modules 를 빌리지 않는다. 메인 폴더 것은 lockfile 보다 오래됐다. 워크트리를 만들면 .env* 를 복사하고 npm ci 를 한 뒤 검증한다.

npm run build 는 추적 중인 파일을 바꾼다. postbuild 의 next-sitemap 이 public/sitemap.xml, public/sitemap-0.xml, public/robots.txt 를 다시 쓴다. 커밋 전에 git status 로 보고 되돌린다.

Production 의 ISR 은 세 번째 요청부터 HIT 다. 캐시 기록이 1~2초 늦다. “두 번째가 HIT 가 아니면 실패”로 판정하지 않는다. Vercel 은 ISR 응답의 cache-control 을 바꿔 보내므로 판정은 x-vercel-cache 와 x-matched-path 로 한다.

Vercel 과 로컬 next start 가 다르게 동작하는 곳이 있다. /KO 는 Vercel 에서 /ko 로 가고 로컬에서는 /KO/vote 로 간다(도착지는 같다). 잘못된 percent-encoding 은 Vercel 이 400 으로 끊는다.

브라우저 자동화의 함정. 링크를 클릭하면 AdSense 전면 광고가 가로챈다. 클라이언트 내비게이션은 window.next.router.push(...) 로 확인한다. /auth/loading 을 code 없이 열면 alert() 가 떠서 자동화가 멈춘다. 기기 언어에 따라 달라지는 동작은 navigator.language 를 고정하고 쿠키를 심어서 본다. 로그인 상태(sb- 쿠키)에서는 돌리지 않는다. 감지 코드가 프로필에 쓴다.

이미지 스모크. /_next/image 를 curl -I 로 치면 콜드 캐시에서 400 이 나온다. 회귀가 아니다. GET 으로 확인한다. CDN 이미지는 https://cdn.picnic.fan/picnic/… 형태여야 200 이다.

Vercel 로그 조회. 전문 검색은 자주 타임아웃한다. 배포 id 로 좁히고 statusCode·requestPath·level 로 묶어 본다. 보존은 약 하루다. 이전 배포 URL 은 SSO 로 막혀 있어 익명 브라우저로 이전 버전과 비교할 수 없다.

환경변수 함정은 지난 핸드오프 §10 이 그대로 유효하다. NEXT_PUBLIC_* 는 빌드 때 인라인되므로 값을 바꾸면 재배포해야 한다. Vercel CLI 로는 이미 있는 변수의 값을 못 바꾼다(REST API 의 PATCH 를 쓴다). 같은 이름의 변수가 대상 환경별로 여러 항목일 수 있다. 이 세션에서 다시 확인하지는 않았다. 덧붙여 zsh 에서 grep --include=*.ts 처럼 따옴표 없는 glob 은 실패한다.

감사 PR 본문의 “교차 리뷰 미실시, 머지 보류” 문구는 낡았다. #86~#95 본문은 사용량 게이트가 막혀 있던 시점에 쓴 것이다. 실제로는 그 뒤 리뷰를 거쳐 머지했다. 리뷰 라운드와 설계 조정은 plan.md §5.4 표에 있다.
